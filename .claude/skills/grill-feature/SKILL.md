<what-to-do>

在我动手写代码之前，把需求拷问清楚。**一次只问一个问题**，等我回答后再问下一个；每个问题都要给出**你推荐的答案和一句理由**（我通常只需要回「可以」或纠正你）。

能用仓库回答的问题**不要问我**——去读代码和你自己的文档，然后把你已经自己答出来的结论列出来让我纠正。

问完的产出不是聊天记录，而是落在仓库里的文档：一份 `docs/spec/<功能>.md`、必要时 1 篇 ADR、`CONTEXT.md` 里的新术语、以及 `docs/roadmap.md` 里的一行。

</what-to-do>

<supporting-info>

## 第 0 步：先自己调研，再开口

按需读（不要为了读而读，发现相关就展开）：

| 文件 | 你从中拿什么 |
|------|--------------|
| `CONTEXT.md` | 本项目的术语表。用户用词与它冲突时**当场指出** |
| `docs/roadmap.md` | 候选功能清单与「下一步建议」，先看这个需求是否已在其中 |
| `docs/spec/*.md` | 各模式的方案与验收，避免重复设计、复用既有交互 |
| `docs/adr/*.md` | 已经拍过的决定。**不要重开已决问题**，除非用户带来新证据 |
| `docs/changelog/*.md` | 历史取舍与实测数字（延迟、窗口尺寸、协议变更的来龙去脉） |
| `tests/` | 现有断言方式：这里的验收标准要能写成同样的离线断言 |
| `web/`、`bridge/` | 代码事实。用户说的行为和代码不一致时，指出来 |

然后**用三五句话汇报你已经自答的部分**：「我读到的现状是 A、B、C；这次需求我理解是 D，不需要问你的地方我按 A/B 走了」——让用户只纠正错的。

## 第 1 步：按依赖顺序走决策树

顺序很重要：后面的问题往往被前面的答案决定。逐层往下，**跳过已被仓库答掉的层**。

1. **触发与场景** — 用户在什么时刻、什么姿势下会用它？（坐在电脑边？演奏中？单手？）
2. **可观测行为** — 用户能看见/听见什么变化？给一个具体场景，逼出边界（「右手拿手机时左手的推子还准吗？」）
3. **数值与协议** — 新的量是什么语义（0=起点还是 0.5=中心）、精度、范围、朝向；走 `kind`/`value_kind` 还是新字段（见 ADR 0003）
4. **边界与失败** — 传感器缺失、未校准、断连、切模式、锁屏、页面回前台，各自应该发生什么
5. **与既有模式的关系** — 是新增第 4 个模式、还是改造 A/B/C？共用前端的哪些链路会被碰到
6. **最小形态与不做** — 现在解锁功能的最小可观测形态；明确写下这次**不做**什么
7. **验收怎么测** — 每条都要能测：离线断言（首选）或一次真机上的是/否问题
8. **真机轮次与发布路径** — 需要几次真机验证、每次之前离线能验证到什么；改动怎么到达用户（源码模式 / exe 快照）

## 第 2 步：拷问纪律

- **必须给推荐答案。** 「你觉得呢？」是我最不想要的回答。推荐 + 一句代价说明，我否掉就是了。
- **不要一次问十个。** 一次一个，等回答。
- **不要问可以自己查的。** 先读代码，再问真正需要我拍板的。
- **发现矛盾立刻停下来指出来**：「代码里 X 是这样，你刚才说的是 Y，哪个对？」「术语表里 `锚点` 指的是校准采样点，你现在指的是什么？」
- **发明具体场景来压边界**：不要问「边界怎么处理？」，要问「如果我翻到一半停住不动 3 秒，CC 应该保持还是回中？」
- **逼出「不做」**：每轮至少问一次「哪些是这次可以先不做的？」
- **对模糊的量词开火**：「更跟手一点」「差不多就行」「偶尔会抖」→ 换成可测量的表述或一次真机判断。
- **每次都要过一遍 [DOCTRINE.md](./DOCTRINE.md)**：那是这个产品 10 轮真机反馈换来的硬约束，凡触及相关领域的决定都要按里面的问法问一次。

## 第 3 步：就地写文档（懒创建，有内容才写）

| 何时 | 写哪里 | 格式 |
|------|--------|------|
| 第一处决策落地 | `docs/spec/<功能>.md` | [REQUIREMENTS-FORMAT.md](./REQUIREMENTS-FORMAT.md) |
| 三条件同时成立 | `docs/adr/NNNN-slug.md` | [ADR-FORMAT.md](./ADR-FORMAT.md) |
| 一个术语被定下来 | `CONTEXT.md` | [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) |
| 需求成立 | `docs/roadmap.md` 加一行 | 照该表现有列 |
| **不要** | `docs/changelog/` | changelog 是**实现之后**写的，需求阶段不碰 |

边定边写，不要攒到最后一次性补——散会时文档必须已经是最新的。

**ADR 三条件（缺一不可）**：难以反悔、没有上下文会让人困惑、是真实取舍的结果。缺任何一条就跳过，别为了仪式感写。

## 第 4 步：开工前的门禁

结束前必须能完整说出下面五项，缺任何一项就**不许说「可以开工」**：

1. **待决问题**：应该为空。还留着就继续问。
2. **非目标**：明确写出这次不做什么（写在 spec 里）。
3. **验收清单**：每条都可测，并标注「离线断言」或「真机 yes/no」。
4. **真机轮次预估**：预计几次、每次要用户做什么动作。
5. **影响面清单**：会改到哪些文件、是否需要重打包 exe、`?v=` 是否要升版、会不会影响 A/B/C 既有手感。

然后停：**需求阶段到此为止，不要顺手开始写实现代码**。用户说「开始做」再进入实现。

## 不要做的事

- 不要写实现步骤（函数名、行号、具体算法）——那是实现阶段的事。spec 里只写行为与协议。
- 不要新建文档体系。用现有的 `docs/spec`、`docs/adr`、`CONTEXT.md`、`docs/roadmap.md`。
- 不要把 `CONTEXT.md` 当 spec 用：它只是术语表，永远不含实现细节与架构决策。
- 不要因为用户说「随便」就自己拍板往下走，也不要在没有推荐答案的情况下等他填。
- 不要问已经在 `docs/adr/` 里定过的事；如果确实是新证据让旧决定过时了，按 ADR 的 supersede 流程走。
