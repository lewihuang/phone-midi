# `CONTEXT.md` 更新规则

`CONTEXT.md` 在仓库根目录，是**唯一的术语表**：某个概念在这个项目里叫什么、指的是什么、不要用哪些同义词。
它**不是** spec、不是设计笔记、不是实现备忘。里面出现实现细节或架构决策就是写错了地方。

只在**一个术语被当场定下来**时更新它，不要攒着。一次改一个词条。

## 现有结构与风格

顶部一句话说明，然后按领域分节，节内用表格：

```md
# CONTEXT — Phone MIDI Controller

项目领域术语表。不含实现细节，不含架构决策。

## <领域名>

<一句话说明这个领域是什么>

| 术语 | 定义 | 输出 / 范围 |
|------|------|-------------|
| **<Term>** | <一两句话，定义它是什么，不是它能干什么> | <x, y, z / 0-16383 / …> |

---

*最后更新: YYYY-MM-DD*
```

现有小节：Sensor Source、Axis、Touch Input、MIDI Target、Mapping、Connectivity、Preset。

## 规则

- **要有主见。** 同一个概念有多个说法时，选一个最好的当词条，其余写进 `_避免_`：
  `**锚点**：…  _避免_：标定点、采样点`
- **定义要短。** 一到两句。定义它**是什么**，不是它能做什么。
- **只收本项目独有的概念。** 通用编程概念（超时、错误类型、工具函数）不进这张表，哪怕项目里到处在用。
  判断标准：这个概念是这个产品特有的，还是任何软件都有的？只有前者才进来。
- **中英混排**：术语可以保留英文原词（`Pitch Bend`、`Bridge`），解释用中文。
- **一个概念一个词条**：如果用户用了与表中冲突的说法，**当场停下来问**是哪个意思，然后决定是改词条还是纠正用户。
- **术语表不含数字**：不写"缓冲 20 ms"这类参数值——那是 spec 的内容。

## 已知缺口（边聊边补）

现有 `CONTEXT.md` 停留在早期（Flutter/UDP 时代的词汇），运行时的核心词汇还没进去。
讨论到下面这些词时，顺手把定义谈清楚并补进表里：

| 待补术语 | 现在口头在用的说法 | 需要定下来的问题 |
|----------|-------------------|------------------|
| 模式 A / B / C | 抬手推子、翻转推子、摇晃弯音 | 名字是否固定？「模式」是产品词还是实现词？ |
| 融合标量 t | `t`、fused t、归一化值 | 与"CC 值"的区别要说清；0/1 的语义随模式不同（见下） |
| 锚点 | anchor、校准点 | 是"一次校准里的采样点"还是"范围端点"？ |
| 校准 profile | lift / flip / shake | profile 与 mode 是不是一一对应？ |
| 数值语义 | unipolar / bipolar | 0=起点 vs 0.5=中心，这是**术语**层面的区分，值得一个词条 |
| 跟手 | 延迟、latency | 产品语言里的"跟手"要不要定义成可测量的量？ |
| 精简模式 | 监视窗、compact | 与"标准窗"的对照关系 |
| Bridge / 手机端 | 服务端、客户端 | 这两个是固定叫法，值得进表 |

补的时候注意：**不要顺便写设计**。如果写着写着发现"这其实是个设计决定"，
那份决定应该进 spec 或 ADR，词条只留一句话的定义。
