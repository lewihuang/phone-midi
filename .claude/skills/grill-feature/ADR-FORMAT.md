# `docs/adr/NNNN-slug.md` 格式

本项目的 ADR 比通用模板**重**：它要能独自解释「为什么当初这么定」，因为很多决定是被真机反馈逼出来的，
半年后回看代码只会觉得奇怪。样式对齐现有三篇：[0001](../../../docs/adr/0001-web-first-architecture.md)、
[0002](../../../docs/adr/0002-json-mapping-config.md)、[0003](../../../docs/adr/0003-explicit-target-kind.md)。

## 编号

扫 `docs/adr/` 取最大编号 +1，四位补零：`0004-<kebab-slug>.md`。目录已存在，不需要懒创建。

## 模板

```md
# ADR NNNN: <一句话决定本身，不是背景>

## 日期

YYYY-MM-DD

## 状态

<已采纳并实现（日期）| 提议中 | 已废弃 | 被 ADR NNNN 取代>；<验证结果，带测试名或数字>

## 背景

问题是什么、现在怎么做、**为什么不够**。每个问题编号，附代码片段或实测证据。
写清楚"如果不改会怎样"——静默错误 > 明显错误的说法在这里特别有效。

## 决策

**一句话把决定说全。** 然后分条展开：

### 1. <面>

<table 或 json 片段>

### 2. 兼容与缺省

缺省值是什么、旧客户端怎么办、**移除条件**是什么（写成可判定的条件，例如"脚本版本升到 vN 之后的下一版"）。

## 备选方案

### 方案 A：<名字>

- 优势：…
- 劣势：…（要具体到"会静默发到错误的 CC"这种程度）

**否决** / **部分采纳**。

（至少写两个真正被考虑过的方案。没有备选方案说明这不是一个真取舍，那就不该写 ADR。）

## 影响

- **前端 / 后端 / 协议**：各自要改什么
- **兼容**：旧版本怎么办
- **解锁**：这个决定让后面什么成为可能
- **文档**：哪些既有文档要跟着改
```

## 什么时候才写 ADR（三条必须全部成立）

1. **难以反悔** —— 以后改主意的代价是有意义的（协议字段、存储格式、架构形状）
2. **没有上下文会让人困惑** —— 未来的人看代码会想「当初为什么这样？」
3. **是真实取舍的结果** —— 确实有别的路可走，你为了具体理由选了这条

缺任何一条就跳过。**可逆的决定不写**——你直接改掉就行。

典型够格的：协议字段的语义（`kind`/`value_kind`）、架构分层（web-first、手机端出语义值）、
存储键与迁移、被否决过的对外约定。
典型不够格的：某个参数取 3.0 而不是 2.5、某个函数拆不拆、UI 上按钮放左还是放右。

## 什么时候用它来 supersede

旧 ADR 的结论被新证据推翻时，**不要改写旧 ADR**：新写一篇，旧的那篇状态改成「被 ADR NNNN 取代」。
`docs/changelog/` 里的历史记录同样只追加、不修改。
