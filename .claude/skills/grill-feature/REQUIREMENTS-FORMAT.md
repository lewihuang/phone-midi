# `docs/spec/<功能>.md` 格式

需求阶段唯一的交付物。**只写行为与协议，不写实现**（不出现函数名、行号、算法细节）。
样式对齐现有 spec：[mode-b-palm-flip.md](../../../docs/spec/mode-b-palm-flip.md)、
[mode-c-shake.md](../../../docs/spec/mode-c-shake.md)。

## 骨架

```md
# <功能名> — 方案与步骤分解

> 状态：<未开始 | Phase N 已实现>；<一句话现状>
> 创建：YYYY-MM-DD
> 关联：[<相关 spec>](...)、[ADR NNNN](...)

---

## 1. 定位

| 维度 | 现状 | 本功能 |
|------|------|--------|
| 用户动作 | … | … |
| 手机端输入 | … | … |
| 输出（协议） | … | … |
| 校准 / 存储 | … | … |

## 2. 背景与问题

为什么要做。**必须带证据**：真机反馈原话、实测数字、复现步骤、相关 changelog 链接。
没有证据的需求先回去问用户。

## 3. 行为规格

用户能观察到的行为，按场景写。每个场景给一个**具体动作**和**预期结果**：

- 场景：<用户做什么> → <看到/听到什么>
- 边界：翻到一半停住 3 秒 / 未校准 / 断连 / 切模式 / 锁屏回来后，各自应该发生什么

## 4. 协议与数据

如果涉及手机 ↔ Bridge 或持久化：

```json
{ "sensor": "…", "axis": "…", "value": 0.42, "kind": "cc", "value_kind": "unipolar" }
```

写清：字段、取值、缺省值、**数值语义**（0=起点还是 0.5=中心）、精度、兼容与迁移。

## 5. 不做（非目标）

显式列出这次**不做**什么。这一节和「做」同样重要，它防止范围爬升。

## 6. 验收

每条都要能测，并标注类型：

| # | 验收项 | 怎么测 |
|---|--------|--------|
| 1 | <性质，而不是数值> | 离线断言（`tests/…`） |
| 2 | <手感/观感> | 真机 yes/no：<用户做什么动作，期望看到什么> |

## 7. 阶段

| Phase | 内容 | 状态 |
|-------|------|------|
| 1 | <最小可交付> | ⬜ |

每阶段都要能独立验证；第一个 Phase 应该是最小可观测形态。

## 8. 开放问题

开工前必须清空。
```

## 规则

- **表格优先**。这个项目的 spec 用表格表达"定位/阶段/验收"，散文只用在背景与取舍。
- **数字必须带单位与来源**：「35 ms（模型实测，见 changelog 2026-09-18）」，不要写「有点慢」。
- **不写实现**。要提到实现位置时只写模块级（"手机端发送路径"），不写函数名。
- **验收里禁止**「更跟手」「更流畅」「更好用」；换成可判定的一句话。
- 写完 `docs/spec/<功能>.md` 后，在 `docs/roadmap.md` 的对应 Phase 或「下一步建议」里加一行指向它。
- 状态行要跟着实现更新，但**不要**在需求阶段预填「已实现」。
