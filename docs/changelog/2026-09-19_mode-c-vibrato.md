关键数字（详见 spec §13）：

- **标定后端到端深度 30.11 cents**（目标 30）；只有另一轴可用时 30.01 → 换轴不改变深度。

## P3 阶段发现并修正的 5 个问题

1. `usable` 映射语义错误（未列出的通道被当成不可用）→ 选不出通道、完全无声。
2. 缓冲区边界取**最旧**样本 → 每个 tick 与最新样本重合时出现 **9.74 cents 单步跳变**（一度被误判为门限斜坡的锅）。同时把"传感器迟到保持"与"插值失败"拆成两个独立计数。
3. 高通预置只对常量成立 → 起手 200 ms 冒出 2.61 cents 假音；新增 `warmupSec = 0.3`（每次启用一次，非每音）。
4. 门限斜坡在 60 Hz 下只有 2.4 个量化步 → 幅度台阶达 42%；新增 `gateMinSteps = 5`。
5. 换轴时两轴可能反相 → 交叉淡化抵消为零深度且方向被静默反转；改为按点积**对齐符号**。

另新增 `stallSec = 0.25`：传感器超过 250 ms 没有新样本（锁屏、WiFi 抖动）就输出中心值，
先发一条 8192 再静默——实测 236 ms 归中，之后不再发送。

## 追加：深度减半（同日真机试听后）

真机反馈："摇晃很丝滑，但映射到 DAW 的值动态过大" → 标称深度 **±30 → ±15 音分**
（真机试听证实 ±30 偏大；古典小提琴揉弦常见 ±10–25）。详细决策与实测见 spec §14。

- `DEFAULTS.nominalCents = 15`；新增 `DEFAULTS.depthTrim`（默认 1.0，作用于**限幅之后**的
  输出倍率，0.5 把整个映射减半、上限一起缩到 ±25；> 1 时硬上限仍锁 ±50）。
- 门限仍按"手劲"判定，与倍率无关；`core` 现在同时暴露 `effortCents`（手劲）与
  `amplitudeCents`（换算倍率后的输出）。
- 旧标定**自动换算**：payload 记录拟合时的标称深度，读到旧的就按 `15/30` 缩放 gain，
  不需要重新校准。
- **主页面新增「深度」输入框**（0.25–2.00，演奏中可改，写入 `pm.vibrato.settings.v1`）；
  调试页同步加了同名滑块。为了"值太大"这种反馈不必再走一次改代码 + 重打包。

套件扩到 **77 项**（58 + 10 + 9）全通过：新增倍率比例性、上限随倍率缩放、倍率下静止仍静默、
门限不随倍率变化、旧标定换算。顺带修掉一个真问题：插值后的钳位原先用未缩放的 `capCents`，
倍率 0.5 时深限幅波形的过冲能冲到 31.21 cents（超过"减半后的上限 25"）。

## 追加 2：修 "摇晃停止后 bend 没有回中"（同日真机反馈）

**症状**：停止摇晃后 DAW 的弯音停在某个值上，不回中心。详见 spec §15。

**先复现再修**（合成信号）：

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 6 Hz 揉弦后接 1.2 Hz 收手慢摆 | 停在 **10.74 cents** | **0.00** |
| 只有 2 Hz / 25 °/s 慢摆 | 持续 **22.06 cents** | 0（0.22 s 内静音） |

**两个原因**：

1. **门限只看幅度**。1–3 Hz 几乎原样穿过 1.5 Hz 高通（2 Hz 93%、3 Hz 102%），而"停止摇晃"时
   手不会瞬间静止（收手、放下手机都是 1–2 Hz 慢动作）→ 门限一直开着，输出变成一个静态偏移。
2. **弯音是 DAW 里的绝对状态**。手机一旦不说话（锁屏 / WiFi 抖动 / 页面冻结 / 定时器被节流），
   最后一条 PB 就一直留着；引擎内的 250 ms 停摆保护救不了"定时器停了"。

**修复**：

- `web/vibrato.js`：门限增加**振荡判定**（带滞回过零 → 半周期中位数 → 速率），速率 < 3.2 Hz
  且信号确实在响且超过 0.22 s 就关门并 **latch**（只有重新安静才解除），避免慢动作反复上冲。
- `bridge/server.py`：**弯音守护**——手机超过 500 ms 没发消息且通道仍弯着就自动归中并告警；
  断连时归中所有弯着的通道；`--pb-idle-ms 0` 关闭。
- `web/app.js`：页面隐藏 / `pagehide` 时立刻发一条中心值（赶在浏览器节流之前）。
- 调试页显示实测振荡频率与 latch 状态，并加「慢速动作：静音 / 允许」开关。

**真揉弦不受影响**：4/5/6 Hz 起振仍是 136 ms、深度满值（判定只需半个周期）。代价是慢速动作
**从静止开始**时仍有 ≤0.22 s、≤8–22 cents 的一段上冲，之后立刻归中且不重复——`oscArmSec`
就是它的旋钮。套件扩到 **95 项**（66 + 15 + 5 + 9）全通过；新增的 `tests/bridge_boot_check.py` 会**真的把 Bridge 起来**抓页面——它当场抓到两个只在启动路径上才暴露的 bug：`--pb-idle-ms` 被读成 `args.pb_idle_sec`（CLI 起不来），以及 `on_startup` 的 lambda 返回 Task 被 aiohttp await，导致**服务端静默挂住不监听**。

## 追加 3：定位澄清——忠实映射，不做"真揉弦"判定（同日，用户决定）

追加 2 的振荡判定加完之后，用户给出了产品定位，**推翻了那一版修法**：

> "放弃去判断哪些动作是真的揉弦，而是忠实地输出所有的手部摇晃。这种条件下的特殊揉弦一定是和普通揉弦
> 不一样的，100% 的弦乐音源本身就带有揉弦功能，如果我需要一个普通的揉弦那么我可以直接使用揉弦功能即可。"

于是：

- **整段移除振荡判定**（`vibratoOnly` / `oscMinHz` / `oscArmSec` 不复存在）。门限回到"手有没有在动"的
  静止检测：低于 `gateCents` → 精确 0（DAW 在中心）；高于它 → **原样送出**，慢速倾斜也是慢速音高。
- 速率测量保留但**只用于显示**（调试页"手动速率 N Hz（仅显示）"）。
- **自动选源优先陀螺**：设备报告了 rotationRate 就只用陀螺通道（加速度只留给无陀螺设备）。
  这是"没回中"最可能的主因——手机转动时重力在轴间的缓慢重分配穿过高通会变成持续偏移。
- 保留 Bridge 弯音守护与页面生命周期归中（它们管的是"手机不说话了"，与动作判定无关）。
- 记录了先行项目调研：Genki Wave 的 Vibrato 是**生成式**（运动强度→揉弦量，回中结构性成立）；
  MidiWrist 用**阈值触发** + 表冠；GitHub 上找不到"跟随式带通直接当弯音"的同类实现。
  我们**故意不走 Genki 那条**：把动作压成"深度"一个标量会丢掉手势本身，而手势正是这个工具的价值。详见 spec §16。

实测：2 Hz 摆 2 s 后手彻底不动 → 之后 350 个 tick **全部精确 0**；2 Hz 慢摆被忠实跟随到 6 Hz 深度的
**93%**（只由高通决定）；静止带噪声 → 0 条消息且自动选源 = gyro。套件 **93 项**（64 + 15 + 5 + 9）全通过。

## 追加 4：回退——恢复旧版 Mode C（同日，用户要求对照 Gitee 旧代码）

用户反馈"现在的错误已经让我无法分析了"，并要求查看 Gitee 上旧版本的代码。核对本地 `origin/master`
（最后一个提交 `2284233 ui迭代`）后发现，**当时能跑的 Mode C 只有 20 行**：

```js
C: { sensor:'accelerometer', axis:'x', unit:'m/s²', inputMin:-40, inputMax:40, pb:true }
function onMotion(e) {
  const acc = e.acceleration || e.accelerationIncludingGravity;   // 已去重力
  if (!acc || acc.x == null) return;
  updateDisplay(acc.x); sendValue(acc.x);                          // 直接线性映射
}
```

**为什么它稳**（这才是关键）：

| | 旧版 | 我换成的揉弦版 |
|---|---|---|
| 信号 | `acceleration.x`（**已去重力**） | 陀螺 6 轴带通 |
| 静止回中 | **结构性**：去重力的加速度静止时就是 0 | 高通 + 幅度门限 + 振荡判定 |
| 噪声 | ±40 m/s² 量程下占 0.1%，听不见 | 需要 calibration、可用性判定、门限 |
| 代码量 | ~20 行 | ~1000 行 |

**决定**：恢复旧版 Mode C 作为默认（`accelerometer/x`、±40、无滤波无校准），只修它真正的问题——延迟。
vibrato 那套（`web/vibrato.js` + `/vibrato-lab.html`）**保留但不再挂在任何模式上**，作为实验件留着。

**延迟的根因与修法**：旧代码有 `SEND_INTERVAL = 16` 的**前沿丢弃**门——窗口内的事件被直接丢掉，
而不是补发最新值，于是更新率被压在 60 Hz 之下并额外加了最多 16 ms。现在 `emitValue` 只做
"变化阈值 + 4 ms 下限"，每个变化的传感器事件都会到 DAW；`SEND_THRESHOLD.C` 从 0.5 降到 0.2 m/s²
（±40 量程的 0.5%，14 位弯音下约 2 音分）。

**验证**（`tests/bridge_protocol_check.py`，跑真实 `MappingEngine`）：

| 项 | 结果 |
|---|---|
| 静止 0 m/s² | **恰好 8192** |
| ±10 m/s² | **±2048 counts**（= 全弯音范围的 ±12.5%，±2 半音下 = ±50 音分） |
| ±0.8 m/s² 以内（Bridge 死区 2%） | 保持居中，抖动不入音 |
| 0→5 m/s² | 单调跟随（0/174/374/578/783/988 counts） |
| 静止噪声 0.7 m/s² | **不发消息** |
| Bridge 的 EMA | 约 1 个采样的延迟（alpha 0.15） |

**教训（写给未来的自己）**：不要用判定系统去替换"物理上本来就成立"的性质。
去重力的加速度静止即 0，这是传感器给的保证；我把它换成旋转信号后，不得不自己造出高通、门限、
振荡判定、latch、起振窗口、校准、可用性判定等一整套东西来重新获得同一个性质——每个零件都是一个
新的失败点，最后连用户都无法分析。**能用物理保证的，不要用逻辑去保证。**
