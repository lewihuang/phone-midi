# 2026-09-17 Mode C 弯音轮化：协议、运行时与校准向导

按 [docs/spec/mode-c-shake.md](../spec/mode-c-shake.md) 与
[ADR 0003](../adr/0003-explicit-target-kind.md) 一次性实现 Phase 1–6。

## 背景

Mode C 原本是"摇晃 → 弯音"，但手机端上送 `axis:'x'`、Bridge 用**来源坐标嗅探**判定弯音，
而 spec 与真机样本都写 `axis:'fused_shake'`。两者一旦对齐就会静默发出 CC1 而非弯音。
此外力度刻度硬编码 ±40 m/s²，且已有样本自相矛盾 3 倍（`anchors` ±56 vs 轨迹 max 20.2），
标定不可自证。

## 实现内容

### Phase 1 — 协议显式声明（ADR 0003）

| 位置 | 变更 |
|------|------|
| `bridge/server.py` | 新增 `FUSED_AXES = (fused_lift, fused_flip, fused_shake)`；`process()` 返回 `(kind, cc, ch, val, norm)` 并按 mapping 的 `target.type` 决定类型；消息 `kind` 优先；旧嗅探保留一版并在首次命中时告警；`set_target` 允许省略 `cc`（弯音仍需 channel） |
| `bridge/config/default.json` | `target` 增 `"type": "cc"` |
| `web/app.js` | 每个数值消息带 `kind` / `value_kind`；C 改走 `fused_shake` + `kind:'pb'` + `value_kind:'bipolar'` |
| `web/index.html` | Ch 选择器独立为 `ch-cfg`（弯音也能选通道），CC 输入仍对 pb 模式隐藏 |

### Phase 2 — 可验证标定

- `robustShakePeaks()`：按方向各裁掉最极端的 10%（`neg_trim` = 负向 p10、`pos_trim` = 正向 p90），
  同时保留原始极值供诊断。
- 5 秒峰值窗口的判定改用**稳健跨度** `pos_trim − neg_trim`，不足 3 m/s² 时拒绝并报出两个跨度。
- 导出（`buildExportJson`）补齐 `source` / `sources` / `robust` / `robust_span` / `window_ms`。
  此前 `source` 只在调试页屏幕上显示、不写进 JSON，导致归档样本无法自证是线性加速度还是重力回退。

### Phase 3 — 线性加速度与自动零位

- 优先 `event.acceleration`；缺失时用 **0.3 Hz 低通估计重力** 再相减（原实现直接使用含重力原始值，
  静止时残留约 9.8 m/s² → 弯音永远偏离中心）。
- **自动零位**：以未校正的线性加速度判定静止（连续 12 帧 < 1.2 m/s² 为静止），
  静止时用 τ=3 s 的低通把 bias 收敛到残差。因不设硬回中（10.1），这是唯一的回中保证。
- 静止判定用未校正值：其幅值与当前 bias 无关，坏 bias 不会把更新逻辑锁死。

### Phase 4 — 自适应增益与 P2 先验

- `scale` 取最近 3 秒 |a| 的 **p95**（不是最大值），分方向估计，限速 5%/s，
  钳制在 [8, 120] m/s²；静止时冻结窗口（否则长期静止会把刻度压到 0）。
- **P2**：收敛值写入 `phone-midi/autoscale/shake/v1`，按**屏幕朝向分桶**；
  启动后前 2 秒为"快速窗口"（30%/s），随后回到 5%/s。
  实现上采用"启动后固定 2 秒快速窗口"而非"检测到 2 倍失配才提速"——行为是后者的超集，
  且无需额外的失配状态机（**与文档描述的偏差，记录在此**）。
- 手动调参与自动值**分开存储**：`phone-midi/tuning/shake/v1`（bendRange / 死区 / 步进 / 静止阈值）
  永不接受自动改写。

### Phase 5 — 主控接入

- `MODES.C`：`axis:'fused_shake'`、`kind:'pb'`、`value_kind:'bipolar'`、`fused:true`。
- 发送阈值改为**输出计数**表达（`minStepCounts`，默认 4）。
- 运行页显示 `轴 / 刻度来源 / 刻度值 / bend 范围`，降级时追加"降级：重力估计"。
- `calMode` 取代布尔 `needsCal`：A/B = `required`（未校准则警告），C = `optional`
  （未校准时徽章显示"自适应"而非"未校准"，并提示刻度会自动适应）。

### Phase 6 — 用户向导

- 新建 `web/calibrate-shake.html`（三步：静止零位 → 演示 ±100% 力度 → 回放校验）。
- `calibrate-wizard.js` 增加 `shake` 分支：单条 devicemotion 处理函数喂**生产运行时**
  （`feedShakeMotion`），录制只是给这条流加个开关，因此向导测的就是线上真实行为；
  第 1 步顺带报出静止残余偏移与加速度来源。
- 第 3 步**回放校验**：保存后立刻再晃 3 秒，算出"你用到 −X% / +Y%"；低于 80% 时提示重做。
- 结果存 `phone-midi/calibration/shake/v2`（`mode:'fixed'`），
  并让 `calibrationDataValid()` 同时接受 v2 固定刻度与调试页的 v1 anchors 两种形状。

## 仿真中发现并修复的问题

| # | 问题 | 影响 | 修复 |
|---|------|------|------|
| 1 | **轴投票被浮点噪声决定** | 静止期把残差≈0 的样本也计入投票，噪声大的一方胜出。重力回退路径上实测轴被钉在 `y`，**整段晃动完全无输出**（PB 恒为 8192） | 只记录真正有运动的样本；要求 1.3× 的明显优势；另加"救援"：晃动中若当前轴已死而另一轴明显有能量，允许切换（此时输出本就居中，不会跳变） |
| 2 | `resetShakeRuntime()` 沿用内存中的先验 | 别的页面/标签写入的先验不会被采用；重置后状态不可直接检查 | 重置时重新从存储读取先验 |
| 3 | 配置文件 BOM 导致启动崩溃 | `json.load(encoding="utf-8")` 拒绝 BOM（PowerShell `Set-Content -Encoding UTF8` 等工具会写入），Bridge 启动即失败 | 改用 `utf-8-sig` |

另记一条**固有物理限制**（非缺陷）：重力回退路径的重力估计是低通，会吸收**持续（DC）加速度**。
摇晃是零均值振荡，因此不受影响；但该路径不能用于"保持某个恒定加速度"的手势。

## 真机反馈后的修复（当日追加）

真机反馈：**「正常摇晃时弯音动态过大」**。定位到两个由本次重构引入的缺陷，都与
"自适应刻度怎么建立"有关，而不是上限设错：

### 缺陷 A（主因）：静止期把刻度预置成 `centroid`，播种逻辑永不触发

`feedShakeMotion` 的兜底会在启动/静止期把两侧刻度填成 `centroid = 40`；
而"首个稳健估计播种"那段代码只在刻度为 `null` 时生效 —— 于是它**永不触发**，
估计器只能以 5%/s 从 40 爬到真实目标（习惯 50 × 余量 2 = 100），**约需 20 秒**。
这段时间里正常摇晃的 `u` 被钳在 1、行程顶满 ±4096。

因为每次开始演奏前必然先静止，这段"过灵敏期"**每次都会重现** —— 这就是感受到的"动态异常大"。

修复：引入独立的 `scaleSeeded` 状态位（不再依赖"是否为 null"），窗口累计 30 样本后
用首个估计**同时**设定两侧，并在播种后给 2 秒快速修正窗口以吸收首估被磕碰带偏的情况。
实测收敛时间由 ~20 s 降到 ~0.5 s。

### 缺陷 B：两侧刻度不对称（并会写入先验长期生效）

`apply(cur, target)` 在 `cur == null` 时直接返回 target（绕过限速）。冷启动第一帧只有正向样本，
于是**正向一帧跳到目标 100，负向无样本 → 落到 `centroid = 40` 再被限速慢爬**：
逐秒实测 `刻度 −42/+100`，负向灵敏度是正向的 2.4 倍，负向行程直接撞顶。
更糟的是这对不对称值会被 `saveAutoscalePrior` 存下并在后续会话加载
（实测存储值 `{scale_neg: 62.1, scale_pos: 100}`），使问题跨会话持续。

修复：播种同时设定两侧；先验存储键升至 **v2**（整批作废 v1 坏值）；
加载先验时校验对称性，`max/min > 1.6` 即丢弃。

### 新增：`adaptiveHeadroom`（默认 ×2）

自适应必须假定"习惯的晃动不是最大力度"，否则正常演奏每次都顶到上限。
刻度改为 `习惯幅度 × 余量`：**正常摇晃只用量程的一半**，只有短促加力才接近上限。
调试页新增「自适应余量」滑杆与「习惯幅度 / 用量%」读数；用量即"近 3 秒峰值占量程比例"，
直接对应验收标准。`scaleMax` 默认由 120 放宽到 200（×2 余量下支持约 100 m/s² 的习惯幅度）。

### 已知取舍（需确认）

自适应窗口 3 秒、限速 5%/s，因此**持续**加大力度会被重新归一化回 50% 用量，
而**短促加力**能冲到上限（实测 3995/4096）。若希望"力度更大 = 弯得更多"且刻度绝对固定，
应使用向导校准（`mode:'fixed'`，不应用余量）或把余量调小。

### 结论：改为**固定刻度**（用户决定）

用户实测后的判断：**「不需要自适应，应当让摇晃有一个固定的值，让用户通过手部动作来输出想要的值」。**

这个判断是对的，而且指出了上面两个缺陷的**共同根源**：自适应测的是"习惯幅度"并据此归一化，
等价于"你越用力、它越迟钝"——持续的力度差异被抹平，力度与输出的对应关系被切断。
对以手感为卖点的控制器来说这是根本性错误。

改动：

- **删除整个自适应机制**：估计器、先验持久化（`phone-midi/autoscale/shake/v2`）、
  余量（`adaptiveHeadroom`）、播种状态、快速修正窗口。不是停用，是删除。
- 新增 `fixedScale`（默认 **40 m/s²**，可调可持久化）：晃到这个幅度 = 跑满 `bendRange`，
  更轻则按比例变小。用户也可用向导校准或调试页的
  **「用近 3 秒峰值填入满量程」**（一键把手感标定下来）。
- 运行期只保留**测量**（近 3 秒 max / p95 与用量%），供 UI 显示与一键填入，**绝不回馈**映射。
- One Euro 默认参数调透明（`mincutoff 12 / beta 3`，原 `6 / 1.2`）：该滤波器在波形峰顶
  （导数≈0）会收紧截止频率、把行程顶部削圆。实测满量程损失由 **−2.3% 降到 −1.0%**，
  使"力度→输出"更接近严格正比。静止抖动由计数域死区负责，提高 mincutoff 没有代价。

### 追加：两个真机问题的修复（同日）

**(1) 普通摇晃就把 bend 撑满 `[−100%, +100%]`**

原因：`fixedScale` 默认 40 m/s² **偏小**——真机上普通摇晃的幅度本身就 ≥40 m/s²，
于是一晃就顶到配置的 bend 上限。旧版把固定 ±40 映射到全 14-bit（±8192），
新版把 ±40 映射到 `bendRange`（默认 ±50% = ±4096），两者对同一动作的输出不同，
所以"和原始版本差异较大"。

修复：

- `fixedScale` 默认 **40 → 80 m/s²**（普通摇晃约用掉一半量程）。
- 调试页把一键标定拆成两个明确语义的按钮：
  **「最大力度 ×2 → 满量程」**（推荐，最大力度只用一半，留余量）与
  **「最大力度 ×1 → 满量程」**（最大力度正好跑满）。
  两者都是**一次性的固定设置**，与自适应无关。
- 两个旋钮分工写进 UI：**固定满量程**管"多大力算满"，**bend 范围**管"满了之后弯多少"。

**(2) 用户校准向导永远报「未收到运动数据，请重试」**

原因：`onShakeAction` 在采集前设 `busy = true`，而抖动处理函数首行是
`if (!sensorActive || busy) return;`——**整个采集期间没有一个样本进入录制缓冲**。
`busy` 本来只用于抑制 A/B 平均采样期间的预览刷新，被误用成了数据通路的闸门。

修复：`onShakeMotion` 只检查 `sensorActive`，不再看 `busy`。
