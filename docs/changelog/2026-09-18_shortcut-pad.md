# 2026-09-18 快捷键面板（Shortcut Pad）实现

## 背景

需求与 13 条决策见 [spec/shortcut-pad.md](../spec/shortcut-pad.md)，触发为什么走 MIDI Note 见
[ADR 0004](../adr/0004-midi-note-triggers.md)。本页记录**实现**：改了什么、测到什么。

一句话：手机/平板变成一块 **8 格（4×2）的宏命令按钮面板**，PC 端把这块面板镜像出来并可编辑，
改完即时同步到手机；按下时 Bridge 发一条 MIDI Note，Nuendo 侧用 MIDI Remote 把那条件映射到宏。

## 改动

### 手机端（新页面）

| 文件 | 内容 |
|------|------|
| `web/pad.html` | 独立页面：大标题 + 4×2 网格 + 底部页签；`100dvh` 单屏不滚动、禁缩放/长按菜单/选中 |
| `web/pad.js` | 渲染 Bridge 下发的布局；`pointerdown` 发 `{kind:'trigger',id,phase:'down'}`、`pointerup` 发 `up`；未连接时格子不可点；断连时先松开所有按住的键**再**断开；忽略不认识的服务器消息（为将来的状态回读留路）；申请 screen wake lock |
| `web/index.html` | 主页加入口「快捷键面板 · 宏命令按钮」 |

按下的判定用 `pointerdown` 而不是 `click`：`click` 在移动端有延迟，而这个功能的全部意义就是"按下即发生"。

### Bridge（`bridge/server.py`）

| 内容 | 说明 |
|------|------|
| `WinMidi.send_note(note, channel, velocity)` | 力度 > 0 发 Note On、= 0 发 Note Off；与 `send_cc` 同一个 `midiOutShortMsg` 位布局 |
| `trigger` 消息分支 | `{"kind":"trigger","id":N,"phase":"down"\|"up"}`，**不进映射引擎**（无范围、无曲线、无平滑），直接变成 Note 36+N / 通道 16 |
| 编号校验 | 越界或非整数编号只记日志，不发消息 |
| `pad_watchdog()` | 手机丢了"松开"（页面被关、WiFi 断、标签页被杀）时 1 秒内补 Note Off——与弯音的 dead-man 定时器同一类兜底；断开连接时也会清扫所有按住的触发 |
| 布局存储 | `%APPDATA%\phone-midi-bridge\pad.json`（与 `window.json` 同一约定；**不能**放 `config/`，那是 exe 的快照目录）。读取时清洗：坏 JSON / 缺格 / 超长文字 / 调色板外的颜色 / 超页数，一律退化或修正，绝不输出不可用的布局 |
| 布局下发 | 连上就发 `{"type":"pad_layout"}`；`broadcast_pad_layout()` 给所有客户端广播（沿用连接时已有的 `{"type":"config"}` 推送机制，没有新链路） |

### PC 端编辑器（Tk）

Bridge 展开态新增「快捷键面板…」按钮 → 独立 Toplevel：页签、页标题输入框、**与手机严格同构的 4×2 格子**、
选中格子的文字输入框 + 8 色固定调色板、每格右下角只读显示 `N36…`。

- 用独立 Toplevel 而不是在主窗里做模式：主窗的几何契约（标准窗固定 480×420 且不记忆位置、
  精简窗记忆尺寸与位置）**一点都没被碰**，这是那八轮真机反馈换来的底线。
- 文字/标题输入做 300 ms 防抖后落盘 + 广播；颜色点击立刻生效。
- 删页要点两次（两次点击确认，而不是可能被 DAW 挡住的模态弹窗）。

### 缓存版本与打包

- 所有页面 `?v=` 统一升到 **23**（含新页面 `pad.js?v=23`）。
- exe 重新打包（**17.87 MB**），归档内 `web/*` 29 个文件与源码**逐字节一致**。

### 测试抓到的两个真 bug

1. **`web/pad.js` 断连时丢掉"松开"**：`ws.onclose` 里先 `ws = null` 再 `releaseAll()`，而 `send()` 在
   没有打开的 socket 时直接返回，于是 up 事件发不出去（服务端 1 秒兜底与断连清扫能救，但手机端的行为是错的）。
   由 `pages_smoke.mjs` 新增的 pointer 事件驱动测试抓到，已修：先松开、再置空。
2. **`BridgeApp._pad_page` 属性与方法同名**：`self._pad_page = 0` 把 `_pad_page()` 方法遮住，
   打开编辑器即 `TypeError: 'int' object is not callable`。由 `bridge_pad_check.py` 的窗口测试抓到，
   方法改名为 `_pad_page_data()`。

## 真机发现的端口泄漏 → 面板改用独立 MIDI 端口（方案 C）

**现象**（用户真机）：Note 36 能正常触发宏 ✓，但 **37 起音源轨跟着弹音**。

**原因**：Bridge 的端口有两个身份——① MIDI Remote 设备的输入；② `All MIDI Inputs` 的一员，
而工程里的音源/乐器轨读 ②，且音源是 **OMNI**，所以**通道 16 拦不住**。Note 36 恰好落在音源键区外
（或作为鼓/键位切换音），37 起落进可弹范围。

**排除的方案 A**：把该端口从 `All MIDI Inputs` 摘掉是标准做法，但用户机器上推子的 CC1 正是靠这条名单
（取消后推子失效，已实测）✗。

**采纳的方案 C：面板用独立 MIDI 输出端口。**

| 改动 | 内容 |
|------|------|
| `WinMidi` 第二个句柄 | `SensorHandler(..., pad_midi=...)`：面板的 Note 走它，推子的 CC/弯音仍走原端口；未配置时退回共用（既有行为） |
| Bridge 设置页 | 新增 **「面板端口」下拉框**（默认「与推子相同」+ 所有输出端口），`_pad_selection()` 解析为 `None` 或端口名 |
| 运行页 | 新增一行状态：`面板端口: PhonePad（与推子分离）`（绿）／`面板端口: 与推子相同（音源轨可能跟着弹音）`（橙）／打开失败时明确写"打不开，暂用推子端口" |
| 命令行 | `--pad-name PhonePad`（打不开则告警并退回推子端口，不阻断启动） |
| 测试 | +7 项：独立端口时 Note **只**出现在面板端口、松开同样、`pad_midi_isolated` 标志、推子 CC 仍走原端口、设置页默认值是两个方向 + 解析逻辑 |

**Nuendo 侧要做的事**（写进指南）：loopMIDI 新建端口（如 `PhonePad`）→ Bridge 面板端口选它 →
给这个新端口**另建一个 MIDI Remote 设备**（推子那个设备别动）→ **不要**给新端口勾 `All MIDI Inputs`
→ 在新设备里重学各条 Note。**推子那条路完全不动。**

### 结论（2026-09-26 晚）：鸿蒙上"网页震动"是死路，查证闭环

用户回传的实测把最后一块补齐了：**10/25/60/200 ms 四档加节奏全都没感觉**；同时**输入法、拨号盘、长按桌面都有触感**
⇒ 马达与系统触感正常 ⇒ 问题在网页这条路本身。查证（三条独立证据）：

1. **华为开发者问答的官方回答**：鸿蒙浏览器**未实现 `navigator.vibrate()`**，要实现振动需用鸿蒙原生 API
   （`vibrator.startVibration()`）。
2. **同一帖提问者的实测**："同一部手机下 Chrome 浏览器也不生效，但是在其它 Android 手机上是生效的"
   —— 顺带替我们省掉了"换浏览器试试"这一步。
3. **我们的自检**：`navigator.vibrate` **存在**、调用返回 **`true`**、零振动 ⇒ 鸿蒙给的是**空壳实现**。

第 3 条是最值得记住的一条：**`typeof navigator.vibrate === 'function'` 在鸿蒙上是假阳性**，
网页端无法自查，只有人手上没感觉才是证据。所以延迟页那套自检的措辞是"调用已接受但手上没感觉"，
而不是"设备不支持"——它本来就不该替用户下结论。

**路线结论**：想要马达震动只有两条原生路（HarmonyOS 4.x 还能侧载 APK → Android 壳 + 原生振动桥；
NEXT 只能 ArkTS `@ohos.vibrator`）。**纯网页能做的只有"确认输入"本身**：声音（Web Audio）或视觉。
用户明确倾向"不做 app"，所以面板继续保留 **形变 + 变暗 + 翻页高亮** 作为不依赖马达的确认，
`navigator.vibrate` 的调用留着（在普通 Android 上仍然有效，且失败时静默）。

## T3 v2.3（2026-09-26）：震动排查第二轮 —— 逐档试出马达吃哪一档

用户真机（安卓 + Edge）反馈：**"自检显示震动 API 可用、安全上下文 yes，但是没有震动感觉，已经将手机
设置为响铃模式"**，另外在系统设置里找到一条"仅为精准操作和重要事件提供触感反馈"并已勾选。

推理链（先把能排除的都排除）：

| 可能性 | 结论 |
|--------|------|
| 浏览器没有这个 API | ✗ 自检显示**可用** |
| 不是安全上下文 | ✗ 自检显示 **yes**（而且震动本来也不要求 HTTPS） |
| 没有用户手势（sticky activation） | ✗ 我们是在 `pointerdown` / `click` 里**同步**调用 |
| 静音 / 勿扰模式 | ✗ 用户已切到响铃模式 |
| **马达做不出太短的脉冲** | **可能是这个** —— 面板原先只振 **10 ms**，有些马达起转就要 20–30 ms，太短等于没按 |
| **系统把触感整体关掉** | **可能是这个** —— 那就连 200 ms 也没感觉（自检能一眼分辨） |

所以这一轮做两件事，都不靠猜：

1. **面板脉冲 10 ms → 25 ms**（`HAPTIC_MS`）。仍是"一点"的确认，但落在大多数马达能起转的区间里。
2. **延迟页的自检改成逐档试**：`10 ms` / `25 ms`（面板用的那一档） / `60 ms` / `200 ms` / `节奏 [30,40,30]`
   五个按钮，每按一次把该档的**返回值含义**写进「上次调用结果」——
   哪一档能感觉到，答案就在哪一档；连 200 ms 都没感觉，就是系统层面把触感关掉了。

仍然坚持的原则：**震动永远只是加分项**。形变（`scale(0.94)`）+ 变暗（`brightness(0.82)`）+ 翻页分段高亮，
这三条不依赖马达，任何设备上都在。

**测试** 262 → **263**：`pages_smoke` 的震动自检断言扩成两条（五档按钮都在；点 25 ms 后文案同时报出
"25 ms / 已接受 / 静音"三类信息）。

## T3 v2.2（2026-09-26）：删掉难看的描边、灰阶加一点点蓝、震动排查

用户真机（**安卓 + Edge**）三条反馈原文：①"点击时在按钮边上出现的高对比度边框非常丑，删了"
②"整体配色饱和度为零有点丑，给整体色调加一点点蓝，只要一点点一点点一点点"
③"我的手机是安卓系统，浏览器是 edge，测试中没有震动"。

| 改动 | 内容 |
|------|------|
| **删描边**（D27） | `.cell.pressed` / `.cell.fired` 的 `box-shadow` 全部去掉。按下的证据只剩**尺寸**（`scale(0.94)`）+ **明暗**（`brightness(0.82)`）；松手后的痕迹改成"压暗一点点"（`brightness(0.93)`）保留 220ms。教训：`inset box-shadow` 会把圆角按钮切成一个方框，白底上跟随字色的那圈近黑尤其刺眼——**"按得出来"和"画个框"是两件事**，边框是我自己加的装饰 |
| **灰阶微蓝**（D28） | `--bg #ececee` → `#eaecf2`、`--fill #e4e4e7` → `#e2e5ee`、`--label #1c1c1e` → `#1c1e26`、次级文字与分隔线同步偏蓝；纯白卡片保持纯白。蓝-红 = +8 / +12（约占量程 3–5%）。纯中性灰就是用户说的"饱和度为零、看着发脏"；iOS 的分组底 `#F2F2F7` 本来就是冷灰。测试加了量级约束：蓝-红必须 > 0 且 ≤ 16，再大就紫了 |
| **震动排查** | 已知：安卓 Edge 支持 Vibration API，且我们是在 `pointerdown` / `click` 里同步调用（满足 MDN 要求的 **sticky user activation**）；Safari 则完全没有这个 API。所以"没震动"只剩两种可能：**调用被拒**（返回 `false`）或**系统层面压掉了**（静音/勿扰/系统里关了振动，或没有马达）。为了不再靠猜，**延迟页新增「⑥ 本机能力自检 — 按键震动」**：显示 API 在不在、是否安全上下文、以及点一下按钮后 `vibrate(200)` 的**返回值含义**（`true` 但手上没感觉 = 系统/硬件；`false` = 调用被拒） |

顺带修掉一处 T3 漏网的旧配色：延迟页结论行里写死的 `style="color:#64748b"`（深色主题时代的石板灰）改成 `class="dim"` 令牌。

**测试** 258 → **262**：`pages_smoke` +4（灰阶微蓝且不过量、按下/松手无描边、延迟页报震动 API、自检文案说明返回值含义）。

## T3 v2.1（2026-09-26）：触觉反馈、默认色改浅、字色跟着填充走

### 第一版错在哪（用户三条反馈，逐条对照）

用户反馈原文：①"这个不是浅色，我说的浅色应当是类似浅灰的颜色" ②"现在所有的按钮都没有点击交互感，
不能让用户仅凭手感或者观察互动来确认" ③"黑体不好看，换成等线字体"。第 ① 条**是我错了**，而且错得可验证：

| 截图 | 平均亮度 | 结论 |
|------|---------|------|
| 改造前（旧深色主题） | 37.7 | 暗底 |
| **我交付的"浅色"第一版** | **32.4** | **暗底 ✗ 比改造前还暗** |
| 修正后 index / 校准页 / 延迟页 | 225.5 / 233.1 / 234.7 / 232.7 / 234.9 | 浅底 ✓ |
| 修正后 pad（在线、用用户当前配色） | 92.7 | 页面底是浅灰（`#ececee` 占 23%），其余是 8 个按钮的填色 |

根因：我在 `ios.css` 里写了两套令牌，其中一套挂在 `@media (prefers-color-scheme: dark)` 下。
渲染环境（和无头截图环境）报的是深色系统 → **整片页面走了深色那一套**，于是我"以为"交的是浅色。
**用户看一眼就发现了，我的自检没发现**——因为当时我只有眼睛没有判据。修正：

1. **只留浅色一套**，`color-scheme: light` 钉死，`prefers-color-scheme` 从手机端 CSS 里彻底删掉（D21）。
   并把这条写成测试：`ios.css` 不许出现 `prefers-color-scheme`、`--bg` 的亮度必须 > 0.8、
   六个手机页面都必须挂 `ios.css`、任何页面都不许带深色分支 —— **这个坑不会再踩第二次**。
2. 反馈②（D22）：格子按下 = `scale(0.94)` + **变深** `brightness(0.82)` + 白色内圈，三件事同时发生；
   松手后留 220 ms 的 `.fired` 痕迹；支持时再 `navigator.vibrate(8)`。
   **变深而不是变亮**是关键：填充色可能是浅色，浅色再提亮就贴到白色，按下去等于没反应。
3. 反馈③（D23）：字体栈等线（`DengXian`）优先，字重按 iOS 字阶压轻（大标题 600、按钮/格子 500）。
4. 顺带按证据修了默认色（D24）：默认色原是深蓝 `#1e293b`（深色主题时代的遗产），
   8 格全用它会把整片浅灰页面压成"偏中"（实测 92.7）；这一轮先换成中性灰 `#8e8e93`、
   预设换成 iOS 系统色，编辑器里格子文字按填充亮度自动切黑/白（`pad_luma()`）。
   **用户已存的颜色不动**——那是用户的配置，不是我的默认值。（下一节里默认色又改成了白色。）

### 顺手抓到的一个工具坑

首次批量截图时，pad 那页拍出来是"未连接"（默认灰 + `.offline` 的 0.4 透明度），看着像样式坏了，
其实是一条**假证据**：`--virtual-time-budget` 会抢在真实 I/O 前面把虚拟时间走完，Bridge 冷启动时
第一次截图的页面可能在 WebSocket 握上手之前就被拍下来了。颜色直方图救了这个判断——
如果只凭"平均亮度"下结论，我会去改一个根本没坏的样式。修法：预算 2500 → 4000 ms，并把 pad 放到最后拍。

### 走通的那条路（照这个顺序做，任何一步颠倒都会失败）

1. **loopMIDI 建面板专用端口**（如 `PhonePad`），与推子端口分开。
2. **重启 Windows MIDI 服务**（管理员）：`Restart-Service midisrv`。
   - 这是本轮最难查的一环：`Windows MIDI 服务` 只在**启动时**把老式（WinMM/loopMIDI）端口包装成新式 MIDI 设备
     （注册表/端口文件里表现为 `MIDIU_KSA_…` 设备实例）。loopMIDI 的虚拟端口**不产生 PnP 到达事件**，
     所以服务不重启，新建端口永远不会出现在 `Windows MIDI` / WinRT 那套枚举里 —— 而 MIDI Remote 用的正是那套。
   - 判据（客观、不用猜）：`%APPDATA%\Steinberg\Nuendo 15_64\Port Setup.xml` 里，新端口是否多出
     `I|Windows MIDI|<端口名>` 一条。只有 `DirectMusic` 一条 = 还没被包装。
   - **重启 Nuendo 没用**（枚举的是服务已经准备好的列表）。
3. **重启 Nuendo**，在 MIDI Remote 管理器里把设备的输入端口选成新端口。
4. **Bridge**：推子端口照旧、**面板端口**选新端口 → START（运行页显示绿色的 `面板端口: …（与推子分离）`）。
5. 手机 `/pad.html` 按格子 → 宏执行 ✓。

### 踩过的坑（都已写进指南）

| 坑 | 表现 | 结论 |
|---|---|---|
| 端口同时是 `All MIDI Inputs` 成员 | 音源轨跟着弹音（OMNI，通道 16 也拦不住） | 必须分端口；**取消 All MIDI Inputs 会弄坏推子**（其 CC1 靠这条名单） |
| 新建端口只被 DirectMusic 枚举 | 往新端口发消息，DAW 完全无反应 | 重启 `midisrv`（见上） |
| `enableemulated` 开关 | **每个端口都多出一份【模拟】副本** | 只挪 `ignoreportfilter`；`enableemulated` 不要碰（这是助手在本轮踩的坑） |
| 先绑"运输状态值" | `Transport.Stop` 用 TriggerPad 绑不生效 | 绑**命令 / 宏**更可靠（真机验证过宏这条路） |
