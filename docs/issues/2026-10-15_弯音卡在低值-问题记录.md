> 报告列的 5 个偏移（`9629177` / `9753441` / `9917741` / `10093039` / `10267960`）**精确对应 153 版**，
> 主工程里只剩 3 个。报告称"共 25 个实例"，实测为 **31**。

**所有偏低实例的取值逐位相同**，跨全部版本都是 `0.2519228458404541`（正常实例一律 `0.5`）：

```
stretchFactor = 0.25 + 0.5 × PB/16383      （rangeFrom=0.25, rangeTo=0.75, source=pitchBend）
0.2519228458404541  →  反推 PB = 63.004  ≈ 63
0.5                 →  反推 PB = 8192（中心）✓ 与"归中即 0.5"自洽
pitchBendRange 全部 = 2.0（±2 半音）→ PB=63 时约 -1.98 半音，与"低 2"吻合
```

报告关于路由的两个数字我复核过：原始字节里 `All MIDI Inputs` **96 次**（报告正确，
它不在解压帧里而在未压缩部分）；`loopMIDI` 1 次。

**值得注意**：这个 63 不是 0，也不是随机的中间值，而是**所有实例逐位相同**。它更像一个固定
来源的写入，而不像"摇晃过程中随机停在某处"。[待确认，见第五节]

## 三、实测复现的代码缺口（Bridge 侧）

用真实 `MappingEngine` + `SensorHandler`（只把 MIDI 输出换成记录器），逐条路径验证：
**PB 弯着时，谁会把它拉回中心？**

| 事件 | 是否归中 | 说明 |
|------|---------|------|
| 手机断开（`centre_pb`） | ✅ | 876 行路径 |
| 手机静默 → 看门狗（`pb_watchdog`） | ✅ | 需 `pb_idle_sec > 0` |
| STOP 清场（`pb_all_centre`） | ✅ | 16 通道各发 8192 |
| **`set_target` 切到 CC** | ❌ **未归中** | 报告点名的缺口 |
| **`set_target` 切通道** | ❌ **未归中** | 报告未提；旧通道会留弯音 |
| **`set_source` 切传感器/轴** | ❌ **未归中** | 报告未提 |
| **「全部停」按钮**（`_on_panic`） | ❌ **未归中** | 只清 Note，不清弯音 |

代码位置：`bridge/server.py` 的 `update_target()` 只做 `self._last_cc.clear()`，从不补发 PB。

### 严重性：比报告说的小，但有个硬缺口

```
pb_idle_sec = 0.5（默认） → 缺口会在 500 ms 后被看门狗兜住   ✅ 实测确认
pb_idle_sec = 0（--pb-idle-ms 0）→ 判定为空、不归中          ❌ 永久留在弯音上
```

也就是说：**只要没关掉看门狗，这些缺口都只是"多弯半秒"**；真正会永久泄漏的前提是
`--pb-idle-ms 0`。

## 四、本次新发现的问题（报告未提）

### 4.1 手机端"主动归中"在 Mode C 下完全不生效 ※ 已实测

`web/app.js` 的 `centrePitchBendNow()` 发的是：

```js
sendMessage({ sensor: 'motion', axis: 'fused_vibrato', value: 0.5, kind: 'pb', ... })
```

而 Mode C 声明的源是 `sensor: 'accelerometer', axis: 'x'`（且 `sendVibratoPb` 用的就是
`m.sensor / m.axis`）。引擎按 `mapping.source` **精确匹配**，源不一致 → 无输出。

忠实复现（先 `set_source('accelerometer','x')`，再发归中消息）：

```
步骤 2：Mode C 摇动        → 发出 PB = [(0, 205)]
步骤 3：centrePitchBendNow → 发出 PB = []   ← 一条都没发！
步骤 4：看门狗 500 ms 后    → 发出 PB = [(0, 8192)]
```

结论：**Mode C 的归中实际全靠 Bridge 看门狗兜底**，手机那句"立即归中"是空转。
（`motion/fused_vibrato` 只在 `web/vibrato-lab.js`（实验室页）里是配套的，不在主页链路。）

### 4.2 手机端 `setMode()` 离开 Mode C 时不补发归中

`setMode()` 只把 `lastSentPb = null`，**一条消息都不发**。而 `centrePitchBendNow()` 有
`currentMode !== 'C'` 守卫，切完模式再调它必然失效——必须在改 `currentMode` 之前调用。

## 五、未确认的关键问题（未来需要证据）

1. **PB≈63 是谁发的？** `.npr` 只存"最终停在这个值"，不记录来源。能连 `loopMIDI Port` 的
   任何程序都可能是发送者（Pianoteq、其他 DAW、硬件控制器）。
   需要：Bridge 侧增加**原始 PB 收发日志**，或复现时用 MIDI 监视器同时抓端口。
2. **为什么是 63 而不是 0 或 8192？** 63 是 7-bit 域里"略低于中心 64"的值，也是 14-bit 域里
   "接近最低"的值。两种解释都对得上，需要现场数据分辨。
3. **为什么所有实例逐位相同？** 指向"单一固定来源"，与"摇晃随机停留"的形态不同。
4. **12:42 保存那一刻，工程里到底有没有弯音？** 报告说"有"，但它的时间证据已被证伪。
   真实会话在 12:05:03 记录的是**「推子目标沿用上次的选择：CC1」**，12:05:44 手机连上后
   一直没断到 14:39；而 Mode C 的弯音**不依赖记忆目标**（每条消息自带 `kind:'pb'`），
   所以"当时在用哪个目标"并不能证明"当时在发弯音"。
   → 仍不能排除"用户正在 Mode C 摇晃中保存了工程"，那样 `.npr` 如实记录当时的弯音值，
     属于**绝对状态被存盘**的固有后果，不是 bug。
5. **报告引用的快照（`midideck-bend/v1_long_151.json` 等）已不存在**，无法复核其提取口径。

## 七、复现方法（留给未来）

```python
# 1) 解压 .npr 读 VSL 参数
import zstandard, json
MAGIC = b"\x28\xb5\x2f\xfd"; dctx = zstandard.ZstdDecompressor()
data = open(r"H:\CuProj\Avis\A03_B01\A03_B01.npr", "rb").read()
offs, i = [], 0
while True:
    j = data.find(MAGIC, i)
    if j < 0: break
    offs.append(j); i = j + 4
for off in offs:
    txt = dctx.decompressobj().decompress(data[off:off+8_000_000]).decode("utf-8", "replace")
    if '"pitchBendRange"' not in txt: continue
    o = json.loads(txt)
    print(off, o["data"]["parameters"]["stretchFactor"])
```
