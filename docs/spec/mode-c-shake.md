## 1. 现状与问题

### 1.1 线上路径（app.js Mode C）

| 维度 | 现状 |
|------|------|
| 上送 | `{sensor:'accelerometer', axis:'x', value: acc.x}`，`acc = event.acceleration \|\| event.accelerationIncludingGravity` |
| 量程 | **硬编码 ±40 m/s²**（页面上可手改） |
| 校准 | 无。`needsCal:false`，主页对 C 隐藏校准入口，无 `/calibrate-shake.html` |
| 轴 | 硬编码 `x` |
| Bridge 判定弯音 | `pb_mode = (sensor == "accelerometer" and axis == "x")` —— **由来源坐标嗅探输出类型** |

### 1.2 已实现但未接线

`fusion.js` 里的 shake 能力已齐全：`PROFILES.shake`、`captureShakePeaksBoth`（5 s 双向 running min/max）、
`computeShakeMotion`、`resolveShakeAxis`（auto/x/y）、`shakeTToPitchBend`；调试页
`/fusion-calibrate-shake.html` 可用；`docs/json.json` 是一份真机样本。

### 1.3 协议耦合（阻断项）

spec 与样本 `recommended_mapping` 都写 `axis:'fused_shake'`，而 Bridge 只对 `axis=='x'` 走弯音。
若把手机端改成 `fused_shake` 而不动 Bridge，会走 `send_cc()` 发出 **CC1 Ch1 的 0–127**；
且 `app.js` 对 `pb:true` 的模式从不发送 `set_target`，目标 CC 完全不受控 —— **静默串到别的参数上**。

**根因**：输出类型（CC / 弯音）由来源坐标推断，而非明示。**已立为 [ADR 0003](../adr/0003-explicit-target-kind.md) 解决。**

### 1.4 标定不可自证（真机样本自相矛盾 3 倍）

`docs/json.json` 同一份文件内：

| 字段 | 值 |
|------|-----|
| `anchors.min / max` | **−52.4 / +59.8**（span 112.2 m/s²） |
| `trajectory` 77 样本 \|a\| | max **20.2**、p50 7.1、p99 20.2 |

两种解释都成立：轨迹是另一次较轻的动作，**或峰值标定被个别尖峰抬高**。文件无法区分——
导出丢掉了 `source`（页面 `fusion-calibrate-shake.js:136` 显示它、`:194` 对 `gravity_delta` 专门告警，
但 `:285` 只导出 `getShakeOpts()`）。

因此 `±40` 的错误方向都判不出来：按 anchors 算只用满 ~67%（**顶部 1/3 行程被削平**）；
按轨迹算满弯只能晃到一半（**永远到不了 100%**）。

**结论**：问题不是"常数选错了"，而是**整条链路没有可验证的标定**。

### 1.5 其余缺陷

| # | 缺陷 | 位置 | 后果 |
|---|------|------|------|
| a | 峰值 = 单样本极值，无稳健统计 | `captureShakePeaksBoth` | 300 样本里最坏的一个决定量程 |
| b | 重力回退不减重力 | `extractMotionDelta(e, null)`（`rest=null`） | 缺 `acceleration` 的设备上**静止时 raw≠0 → 回中不是 8192 → 持续跑调** |
| c | 轴硬编码 `x` | `app.js` | 握姿/朝向变化即失效（`resolveShakeAxis` 已实现却没用） |
| d | 阈值用输入物理量表达 | `SEND_THRESHOLD.C = 0.5 m/s²` | 换算到输出是 **约 70–100 个 PB 计数**（`scale` 40–56 时）的死区，吃掉 14-bit 精度 |
| e | 无用户入口 | `app.js:147` `needsCal:false` | 唯一旋钮是裸 m/s² 输入框，与本文件原设计原则「无需理解 m/s²」冲突 |

## 2. 目标与非目标

### 目标

| # | 目标 |
|---|------|
| G1 | **静止即精确居中**：PB = 8192（容差见第 7 节），不因握姿微变而漂移 |
| G2 | 晃动 → 双向 bend，满力度到达**配置的 bend 范围**（默认 ±50%，见 5.1） |
| G3 | **开箱可用**：默认固定刻度 40 m/s² 即可用，无需校准 |
| G4 | **可选向导**按自己的力度标定一次，与 A/B 的交互一致，主页显示"已校准" |
| G5 | 缺 `acceleration` 的设备上仍满足 G1（降级路径必须零点正确，且状态可见） |
| G6 | 端到端延迟与 Mode B 同量级（t90 ≤ 40 ms，可用 `/latency.html` 实测） |
| G7 | 协议不再靠来源坐标推断输出类型（ADR 0003） |

### 非目标

- 不做"摇晃 → CC"（ADR 0003 让协议自然支持，但不在本轮）
- 不做多轴合成 bend（只取单主轴；`resolveShakeAxis` 的 auto 已足够）
- 不做手势识别/节拍检测
- **不做硬回中**（见 10.1）
- 不改 Mode A/B 的语义与存储格式

## 3. 协议变更（已定，详见 ADR 0003）

消息显式声明输出类型与数值语义，废弃来源坐标嗅探：

```json
{ "sensor": "accelerometer", "axis": "fused_shake", "value": 0.62,
  "kind": "pb", "value_kind": "bipolar" }
```

- `kind`: `"cc"` \| `"pb"` —— 取代 `sensor=='accelerometer' and axis=='x'` 嗅探；
- `value_kind`: `"unipolar"`（0=起点/1=终点，A/B 推子）\| `"bipolar"`（0.5=中心，C 弯音）；
- 配置的 `target.type` 作为缺省，运行时 `kind` 优先；
- 缺 `kind` 时回退旧嗅探 + deprecation 日志，前端升版后移除；
- **`fused_shake` 纳入"不过 Bridge 平滑"的轴集合**（平滑属手机端职责）。

完整取舍与备选方案见 [ADR 0003](../adr/0003-explicit-target-kind.md)。

## 4. 信号链（手机端）

```
devicemotion
  → ① 线性加速度提取        a = acceleration，否则 高通估计（见 4.1）
  → ② 自动零位              a ← a − bias（静止时缓慢估计，见 4.1）
  → ③ 主轴选择              axis ∈ {x, y}，滑动窗能量投票 + 用户可锁定
  → ④ 归一化                u = a_axis / scale        scale 由 4.2 决定
  → ⑤ 整形                  u' = deadband + 曲线      （第 5 节）
  → ⑥ t = 0.5 + 0.5·clamp(u', −1, 1)
  → ⑦ 平滑/限速             One Euro（复用 Mode B 调参基础设施）
  → ⑧ 发送                  { …, kind:'pb', value_kind:'bipolar' }，按输出步进节流（第 6 节）
```

Bridge：`PB = 8192 + round(bendRange·(2t−1)·8192)`，变化检测按 14-bit 精度（已修复）。

### 4.1 线性加速度与自动零位

- **优先** `event.acceleration`（线性加速度，已去重力）。
- **回退**（`acceleration` 缺失）：**不得**直接使用含重力原始值。改用高通估计：
  维护重力估计 `ĝ`（对 `accelerationIncludingGravity` 做低通，截止约 0.3 Hz），
  `a = a_includingGravity − ĝ`。该估计有延迟与漂移，故：
  - 标记 `source: 'gravity_delta'`，并在运行页明示"降级：重力估计"；
  - 仍须满足 G1。
- **自动零位**：静止检测（连续 N 帧 |a| 低于静止阈值）时，用慢速低通把残差归零（bias 估计）。
  **这是"不跑调"的最终保证**，也是 G5 的实现手段。
- **因为不做硬回中（10.1），自动零位是唯一的回中保证** —— 它必须被验收覆盖（A9/A10），
  而不是"锦上添花"。
- 两条路径都必须在静止时给出 `a ≈ 0`；无法满足时（权限拒绝、传感器不可用）**明确报错**，不静默降级。

### 4.2 力度刻度 `scale`

**固定刻度（已定，2026-09-17 真机反馈后确定）**

```
scale = 向导校准值（若已校准，可按方向不同）
      = tuning.fixedScale（否则，默认 40 m/s²）
u     = a / scale            → clamp(−1, 1)
PB    = 8192 + round(bendRange · u · 8192)
```

- **不做任何运行时估计**：力度 → 输出是严格的正比函数，用户用手的动作决定输出值。
- `fixedScale` 默认 **80 m/s²**（真机反馈：普通摇晃幅度约 40 m/s²，
  若默认 40 则一晃即满，故留一倍余量），可在调试页调整，持久化于
  `phone-midi/tuning/shake/v1`。
- 调试页提供两个一次性标定按钮：**最大力度 ×2 → 满量程**（推荐，留余量）与
  **最大力度 ×1 → 满量程**；等价的滑杆可手动微调。
- 向导校准（`mode:'fixed'` 的 `scale_neg/scale_pos`）存在时覆盖 `fixedScale`，
  允许正负不对称（真机样本即 −52.4 / +59.8）。二者都**恒定**，不随演奏漂移。
- 运行期只做**测量**（`measureMotion`：近 3 秒的 max / p95 与用量%），
  供 UI 显示与一键标定用，**绝不回馈**到映射。

**两个旋钮的分工**（请在 UI/文档中保持这个区分）：

| 旋钮 | 含义 |
|------|------|
| `fixedScale`（固定满量程） | 晃多大力算"满"——决定**输入刻度** |
| `bendRange`（bend 范围） | "满"之后弯多少——决定**输出上限** |

**为什么放弃自适应**（原设计为自适应增益 + 余量，真机实测后否决）：
自适应估计器测的是"用户**习惯**的幅度"，并据此归一化。其后果是**你越用力、它越迟钝**——
持续的力度差异会被抹平回同一个用量，力度与输出的对应关系被切断。
对乐器而言这正是要否定的：固定刻度才有可预期的、可重复的力度响应。
代价是用户需要（一次性）设定刻度，用默认 80 m/s² 或按自己力度标定一次即可。

**可选：三步向导（精调）**

与 A/B 同构，profile 复用 `PROFILES.shake`：

| 步骤 | 内容 |
|------|------|
| 1 | 静止确认零位（同时用于诊断：展示当前 `source` 与残差） |
| 2 | 演示「±100% 满弯音」力度（5 s 双向），记录**稳健峰值**（每方向 p95，或每周期峰值的中位数） |
| 3 | **回放校验**：请用户再晃一次，显示"你刚才用到 ±X%"；若 < 80% 提示重做 |

- 保存为 `mode:'fixed'` 的 `scale_neg` / `scale_pos`（允许正负不对称，真机样本即 −52.4 / +59.8）；
- 未校准或选择自适应时用 `mode:'auto'`；
- 存储：`phone-midi/calibration/shake/v2`（v1 为调试页导出格式，不可直接复用为运行时校准）。

## 5. 整形、回中与 bend 范围

| 环节 | 规则 |
|------|------|
| 中心死区 | 用**输出计数**表达（建议 ±30 计数），且**相对当前有效行程**（`bendRange·8192`）而非 16384 |
| 曲线 | 默认线性；预留 `exp`/`log` 供手感调整（复用 mapping 的 curve 语义） |
| 回中 | **仅物理回中**：静止 → `a≈0` → `t=0.5` → PB 8192。**不做硬回中**（10.1） |
| 平滑 | One Euro：静止平滑、动起来跟手；参数比 Mode B 更偏响应（弯音要求即时） |
| 输出范围 | `bendRange` 限幅，见 5.1 |

### 5.1 bend 范围（已定：默认 ±50%，可在调试中修改）

输出公式：

```
PB = 8192 + round( bendRange · (2t − 1) · 8192 )
```

- **默认 `bendRange = 0.5`** → 满力度输出 `PB ∈ [4096, 12288]`。
- **语义**：满力度晃动只产生 DAW 弯音范围的 ±50%。这与输入侧力度无关——
  "晃多猛算满"由 `scale`（4.2）决定，`bendRange` 只管**输出幅度上限**。
- **与 DAW 的关系（必须在 UI 上提示）**：DAW 的 pitch bend range（常见 ±2 半音）决定
  PB 0…16383 的音乐含义。`bendRange=0.5` + DAW ±2 半音 ⇒ 满晃 = **±1 半音**。
  若希望满晃 = ±2 半音，把 `bendRange` 设回 1.0，或把 DAW 的范围设成 ±4。
  不写清这一条，用户会把"晃到底只弯一个半音"当成 bug。
- **诚实说明的副作用**：限制到 ±50% **不会提高分辨率**。每个 PB 计数对应的音高变化由 DAW 的
  弯音范围决定，与 `bendRange` 无关；限制范围只是让行程变短。它的价值是
  **安全上限 + 手感可控**（猛晃不会甩出夸张的音高偏移）。
- **可调位置**（因为你会按调试结果改这个值）：
  - 运行时调参 API `setShakeTuning({ bendRange, … })`，与 Mode B 的 `setFlipTuning` 同构、
    同样用 localStorage 持久化（`phone-midi/tuning/shake/v1`）；
  - 调试页 `/fusion-calibrate-shake.html` 增加滑杆（与现有的投影轴、中心死区并列）；
  - 可选：在 `/latency.html` 也放一组，便于真机 A/B 对比手感。
- 预留每侧独立 `bendRangeNeg` / `bendRangePos` 以适配真机非对称力度；默认单值。
- 上下限必须被 clamp（`bendRange ∈ [0.05, 1.0]`）。

## 6. 精度与发送节流

- PB 为 14-bit（16384 级）。Bridge 的变化检测按 **16383 精度**判定（已修复）。
- 手机端发送阈值改为**输出步进**表达，且相对**有效行程**：建议 `minPBStep = 4` 计数
  （占 `bendRange·8192` 的约 0.05%），可配置；**不再**用 `0.5 m/s²` 这类输入侧物理量（缺陷 d）。
- 限速：沿用 `MIN_SEND_INTERVAL_MS`（硬地板，防极端高频），实际节流交给输出步进判断。

## 7. 验收标准（可测）

| # | 指标 | 阈值 |
|---|------|------|
| A1 | 静止 10 s 的 PB 稳定性 | 稳定在 8192 ± **16** 计数内，且不随轻微握姿变化漂移 |
| A2 | 力度 → 行程 | **严格正比**：幅度 = `fixedScale` 时到达 `8192 ± bendRange·8192`；幅度减半则行程减半（实测偏差 −1.0%~−2.2%，来自 One Euro 在峰顶的轻微削圆） |
| A2b | 两方向对称 | 同一 `fixedScale` 下正负行程一致（校准可分别设定时按校准值） |
| A2c | 无冷启动 | 首个样本即按固定刻度换算，不存在收敛期 |
| A3 | 刻度一致性 | 同一人两次向导校准的 scale 差异 ≤ 15% |
| A4 | 轴自适应 | 竖握/横握各测一次，主轴判定正确 |
| A5 | **降级路径** `gravity_delta` | 静止时 PB 仍满足 A1（"不跑调"的硬指标） |
| A6 | 协议 | `kind:'pb'` 走 `send_pitch_bend`；`axis:'fused_shake'` 且缺 `kind` 时**不得**静默发 CC（警告 + 忽略，或按配置默认） |
| A7 | 端到端延迟 | `/latency.html` 实测 t90 ≤ 40 ms |
| A8 | 导出可自证 | 新样本含 `source`、窗口长度、样本数、分位数，且能用它复核 scale |
| A9 | **无硬回中的长时漂移** | 连续 60 s（含多次停晃）后静止 PB 仍在 8192 ± 16 —— 这是 10.1 决策的代价，必须测 |
| A10 | 回中速度 | 停止晃动后 ≤ 300 ms 回到 8192 ± 16（用物理回中替代硬回中后的手感指标） |
| A11 | bend 范围可调 | 调试页改 `bendRange` 后立即生效，且超调被 clamp 到 `[0.05, 1.0]` |

| 6 | 用户向导页 + 回放校验 + 主页校准状态 | 2、4 | ✅ |
| 7 | 真机验收（含人为构造的降级场景，A1–A11） | 全部 | ⏳ 待真机 |

Phase 1–4 与产品定位无关，做完只会更对；Phase 5 起才改变用户体验。

### 9.1 实现与本文档的偏差（记录）

1. **轴切换的额外规则**：文档只写"仅静止时应用投票"。实现另加一条**救援规则**——
   晃动中若当前轴已明显死掉（幅值低于静止阈值）而另一轴能量大于其 3 倍，则允许切换。
   理由：连续晃动时永远等不到静止，若初始轴向判断错误将全程无输出；而该情形下输出本就在中心，
   切换不会产生跳变。
2. **自适应增益已整体移除**（原 4.2 与 10.3 的设计）：真机实测后改为固定刻度，理由见 4.2
   与 10.3。相关代码（估计器、先验持久化、余量）已删除，不是停用。
3. **One Euro 默认参数更透明**（`mincutoff 12 / beta 3`，原 `6 / 1.2`）：
   该滤波器在波形峰顶（导数≈0）会收紧截止频率，把行程顶部削圆。
   实测满量程损失由 −2.3% 降到 −1.0%，使"力度→输出"更接近严格正比。
   静止抖动由计数域死区负责，因此提高 mincutoff 没有代价。

## 10. 决策记录

### 10.1 不做硬回中 —— ✅ 已定（2026-09-17）

不做"停晃 N ms 后强制回到 8192"的定时兜底：它会与物理回中叠加，产生依赖时序的边界 bug。

**代价与补偿**：物理回中（4.1 的自动零位）成为**唯一**的回中保证，因此

- 自动零位从"优化项"升级为**必须正确实现**的核心环节；
- 新增验收 **A9**（连续 60 s 含停晃后仍居中）与 **A10**（停晃后 ≤300 ms 回中），
  替代原本由硬回中兜住的场景。

### 10.2 bend 范围默认 ±50%，且必须可在调试中修改 —— ✅ 已定（2026-09-17）

见 5.1。要点：`bendRange = 0.5` 为默认；通过 `setShakeTuning` 持久化 + 调试页滑杆调整；
必须 clamp 到 `[0.05, 1.0]`；UI 需说明它与 DAW pitch bend range 的关系
（默认 ±50% × DAW ±2 半音 = ±1 半音）。

### 10.3 自适应 `scale` 的持久化方案 —— ⛔ 已作废（2026-09-17，被 10.5 取代）

（历史记录）曾决定采用 P2：自适应刻度存入 `phone-midi/autoscale/shake/v1` 作为先验、
按屏幕朝向分桶、启动后 2 秒快速再收敛。该方案随**自适应本身被否决**而整体作废（见 10.5），
相关代码与存储键已删除，`v1` 键中可能残留的旧数据不再被任何代码读取。

作废前的实测结论保留作为参考：自适应估计器有 4.2 所述的根本问题，
且其冷启动若处理不当（两侧刻度不一致、或从 `centroid` 限速爬升）会产生
"一侧灵敏 2.4 倍"与"约 20 秒过灵敏期"两类缺陷。

### 10.5 采用**固定刻度**，放弃自适应 —— ✅ 已定（2026-09-17，真机反馈后）

用户实测结论：**「不需要自适应，应当让摇晃有一个固定的值，让用户通过手部动作来输出想要的值」**。

**理由**：自适应测的是"习惯幅度"并据此归一化，等价于"你越用力、它越迟钝"——
持续的力度差异被抹平，力度与输出的对应关系被切断。对以手感为卖点的控制器而言这是根本性错误：
固定刻度才能提供可预期、可重复的力度响应。

**实现**：`fixedScale`（默认 40 m/s²，可调可持久化）或向导校准值；映射严格正比；
运行期只测量不反馈。详见 4.2。

**代价**：用户需一次性设定刻度（默认值即可用，或按自己力度标定/一键按峰值填入）。
**收益**：无冷启动、无漂移、无跨会话坏先验，且删除了估计器、先验、余量三套机制——
真机反馈中出现的两类缺陷（见 changelog）随之从根本上消失。

### 10.4 协议变更单独立为 ADR —— ✅ 已定（2026-09-17）

已创建 [ADR 0003: 输出类型由协议显式声明，废弃来源坐标嗅探](../adr/0003-explicit-target-kind.md)。
