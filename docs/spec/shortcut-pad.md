## 1. 定位

| 维度 | 现状（传感器模式 A/B/C） | 本功能（快捷键面板） |
|------|--------------------------|----------------------|
| 用户动作 | 抬起 / 翻转 / 摇晃手机 | **点击屏幕上的按钮** |
| 手机端输入 | 传感器（姿态 / 加速度） | 触摸 |
| 输出语义 | 连续值 `t ∈ [0,1]` → CC / 弯音 | **离散触发**：一次点击 = 一个触发编号 |
| 手机端 UI | 主页：选模式 → 校准 → 启动 → 数值页 | **独立页面**，与主页互不干扰 |
| 校准 / 存储 | 需要校准（lift / flip / shake profile） | **不需要校准**，不写模式 profile |
| DAW 侧一次性工作 | 把 CC / 弯音映射到参数 | 把**触发编号**映射到宏 / 命令 |

**参照物**：Elgato Stream Deck —— 一块按钮阵列，每个按钮打一个动作。本功能用手机/平板的屏幕当那块阵列，动作经**现有 MIDI 管道**进入 DAW。

---

## 2. 背景与问题

在 DAW 里为单个动作（例：把当前轨道变红）去够鼠标或键盘，会打断编曲/混音的手感。用户已经在工程逻辑管理器里建好了宏，希望把它绑到手机上——而这台手机本来就摆在 DAW 旁边当额外输入设备。

关键边界：**宏是 DAW 侧概念，手机不感知宏**。手机只发一个触发编号，"这个编号 = 哪个宏"由 DAW 侧一次性映射决定（见 `CONTEXT.md` 的 Macro / Trigger 词条）。

---

## 3. 已定的决策

| # | 决策 | 依据 |
|---|------|------|
| **D1** | 触发经 **MIDI Note** 走现有管道：手机 → Bridge → loopMIDI → Nuendo | MIDI Remote 可以把**任意 Key Command（含宏）**分配给一个 MIDI 消息（[Steinberg 论坛答复](https://forums.steinberg.net/t/resolved-use-midi-controller-to-activate-macro/888889/2)、[Nuendo 13 映射助手文档](https://archive.steinberg.help/nuendo/v13/de/cubase_nuendo/topics/midi_remote/midi_remote_mapping_pages_r.html)）。不引入键盘注入、不需要焦点判定、不新增权限。**真机验证（2026-09-18，Nuendo 15）**：MIDI Remote 管理器与映射助手存在；控制可学习 **Note / Bend / Aftertouch**；元素类型可选 **按钮 / 推子 / 触发 Pad**（触发 Pad 对应我们的"按下即发"） |
| **D2** | 手机只上送**触发编号**，Bridge 负责映射成具体 MIDI 消息 | 沿用 ADR 0003 的分层：手机出语义，Bridge 出 MIDI |
| **D3** | **独立页面**，与 A/B/C 无关，不做共存协调 | 用户：新功能与原推子无关，"类似 Stream Deck"；用宏时不在用推子 |
| **D4** | 不需要校准，不写模式 profile | 面板不读传感器 |
| **D5** | 面板固定 **2 列 × 4 行 = 8 格/页**（原 4×2，见 D15）；**页数固定 6 页 = 48 个按钮**（原设计为"多页、上限 8、可增删"，见 D18））；每页有**大标题**说明该页用途 | 用户：近期只需 8 个宏；翻页为将来留 |
| **D6** | 每格的**显示方式可配置**：文字标签与按钮颜色 | 用户：可能需要改按钮显示（文本或颜色） |
| **D7** | 配置**住在 PC / Bridge 侧**，PC 端把手机页面**镜像**出来并可视化编辑，**改动即时同步到手机** | 用户明确要求；也让"在 PC 上看得到手机长什么样"成为附带价值（与精简监视窗同一思路） |
| **D8** | 布局数据存 `%APPDATA%\phone-midi-bridge\pad.json` | 与 `window.json` 同一约定；exe 的 `config/` 是快照目录，不能存用户数据（见 changelog 2026-09-17 的打包说明） |
| **D9** | 手机端入口是独立页面 `/pad.html`（主页加入口链接，Bridge GUI 显示该 URL） | 不改动主页 A/B/C 的任何链路 |
| **D10** | **一个按钮 = 一个触发 = DAW 侧一个宏**；宏里的几十个动作由 DAW 自己跑。**Bridge 侧不做复合动作**（一次按下发多条 / 带延时 / 按条件） | 宏需要的上下文（当前轨道、选中项、工程状态）只有 DAW 知道；Bridge 是无状态盲转发。Stream Deck 需要多动作是因为它跨应用，我们的动作全在 DAW 内。协议留了扩展位 |
| **D11** | 颜色是**纯显示**（用户自选，为了快速认出功能），**不带语义**（不做"红色=危险"这类含义） | 用户：不需要刻板印象 |
| **D12** | **不做误触保护**（无长按确认、无锁定开关） | 用户：会看着手机操作 |
| **D13** | **状态回读（State Read-back）v1 不做，但已确认未来需要**（未来会有开关型宏：solo / 录音预备 / 监听 / 循环） | 用户：未来会有开关型，v1 可以先不做。**方向记录在案**，将来单独排期——它要先解决 loopMIDI 回环端口的划分，并给 Bridge 增加 MIDI 输入 |
| **D14** | 面板**优先使用独立的 MIDI 输出端口**（Bridge 设置页的「面板端口」下拉框、CLI 的 `--pad-name`）；默认仍是"与推子共用"以保持既有行为 | **真机发现**：Bridge 的端口同时是 MIDI Remote 设备输入与 `All MIDI Inputs` 成员，而音源轨读后者且为 OMNI —— 通道 16 也拦不住，于是按面板时音源跟着弹音（Note 36 落在键区外、37 起开始弹）。取消 `All MIDI Inputs` 会**弄坏推子**（其 CC1 靠这条名单，真机已验证），所以必须分成两个端口 |
| **D15** | 面板布局 **2 列 × 4 行**（原 4×2）；格子数仍 8，只改形状；**手机与 PC 编辑器同构** | 用户真机后提出：4×2 铺满整屏时按钮扁而宽，浪费手机竖向空间。改动面四处：`pad.html` 的 CSS 网格、`pad.js` 的 `COLS/ROWS`、`server.py` 编辑器的 `slot // PAD_COLS`、以及断言形状的测试 |
| **D16** | **每格有自己的音符编号**（`cells[i].note`，0–127），与格子位置**解绑**；缺省时按位置取 `36 + 触发编号`（旧配置行为不变） | 用户要求：编号要能在 PC 端改。解绑带来两个好处：**挪按钮位置不必在 DAW 里重学**、能把编号挪出音源的键区。代价：配置多一个字段 + 需校验重复/越界；改编号本身仍需在 DAW 侧重学一次（无法避免）。**按住期间若改了编号，松开仍关掉当初发出的那一条**（否则 DAW 里留悬挂） |
| **D17** | **拖动换位 = 两格交换**（PC 编辑器里拖），落下即交换整格内容（文字 + 颜色 + 音符） | iOS 那种"插入并顺移"的前提是有无限翻页接住被挤出的图标，而这里只有固定 8 格；交换是唯一不引入额外规则、且绝不丢内容的做法。**只在 PC 端拖**（手机是哑显示端）、**只在当前页内拖**（跨页留待以后） |
| **D18** | **页数固定 6 页（共 48 个按钮），不做"加页/删页"** | 用户：48 个按钮应该够了，去掉增删页的功能。配置里页数不足会被补齐、多余会被丢掉；编号上限随之变成 48（音符 36–83）。好处：手机与 PC 永远是同一套结构，没有"某页只在一端存在"的状态 |
| **D19** | **音符编号不在手机上显示**（只有 PC 编辑器显示） | 用户：手机端按钮右下角不需要角标，只在 PC 端提示即可。理由成立——编号是"配置期信息"（在 Nuendo 里对照学习用），不是"演奏期信息"，放在按钮上会干扰"一眼认出这个按钮" |
| **D20** | 按钮颜色**不再限死 8 色调色板**：PC 端可**取色器**或**手输 hex**（`#rgb` / `#rrggbb`），`pad.json` 存任意合法 hex | 用户：着色要更自由、更复杂（选了"任意颜色"这一档，不做渐变、不做 WebGL 着色器）。校验**只放行合法 hex**——这个字符串会写进手机上的 `style.background`，放开成任意 CSS 就是一条注入通道；8 个原色降级为编辑器里的**预设色块**（快捷方式，不是白名单） |
| **D21** | 手机端视觉**只有浅色一套**，**不跟随系统深色**（`color-scheme: light` 钉死，代码里不许再出现 `prefers-color-scheme` 的第二套令牌） | T3 第一版写了深色分支，结果在深色系统上把整片页面渲染成黑底——用户第一句反馈就是"这个不是浅色，我说的浅色应当是类似浅灰的颜色"。**这不是口味问题，是照错了源**：iOS 的浅色是浅灰分组底（`#ececee` 附近）+ 纯白卡片，深色主题是另一套东西。现在有一张无头截图 + 平均亮度做客观判据（`tools/luminance.mjs`，浅底 >180），并有测试守住这条 |
| **D22** | 按下必须有**看得见也摸得着**的反馈：格子 `scale(0.94)` + **变深**（`brightness(0.82)`）+ 白色内圈；松手后留 220ms 的"已发出"痕迹；支持时再 `navigator.vibrate(8)` | 用户："现在所有的按钮都没有点击交互感，不能让用户仅凭手感或者观察互动来确认"。要点是**变深而不是变亮**——填充色可能是浅色，浅色再提亮就贴到白色，按下去等于没反应。三条反馈（形变/明暗/内圈）同时发生，即使眼睛没看屏幕、只靠余光也能确认 |
| **D23** | 字体栈**等线（DengXian）优先**，字号字重按 iOS 字阶（大标题 600、按钮/格子 500） | 用户："黑体不好看，换成等线字体"。Windows 上没有 SF Pro，等线是系统自带里最接近"轻、干净"的一档；iOS 上仍然落到系统 SF 字体 |
| **D24** | 编辑器**预设色**换成 iOS 系统色，默认色 = 中性灰 `#8e8e93`（原默认深蓝 `#1e293b` 退役）；格子文字颜色按填充色亮度自适应（浅底深字、深底白字） | 浅色页面上 8 个深蓝块会把整页压成"暗底"（截图实测平均亮度 92.7 vs 其他页面 225–235）。默认色是"还没配过色"的那一档；用户想区分功能时再挑彩色。**已存的格子颜色不会被改**（那是用户配置） |
| **D25** | **触觉反馈**：按任意格子、以及**翻页**（分段控件）时各振动一下（`navigator.vibrate`，**25ms**）；API 不存在、返回 `false`、或被系统压掉时静默跳过。**但这条路在鸿蒙上是死的，见下** | 用户："点击任意按钮以及选择分页是否可以加入手机震动来确认输入"。翻页也算——它同样是一次"我按到了"的确认。**排查结论（2026-09-26，真机 = HarmonyOS + Edge）**：自检显示 API **可用**、安全上下文 **yes**、调用返回 **true**，但 10/25/60/200ms 四档加节奏**全都没感觉**。查证后确认这是**平台限制**：华为开发者问答的官方回答明确说鸿蒙的浏览器**未实现 `navigator.vibrate()`**，要实现振动得用鸿蒙原生 API（`vibrator.startVibration()`）；同一帖里的提问者实测**同一部手机上 Chrome 也不生效**（其它 Android 手机正常）。也就是说鸿蒙给的是**空壳实现**——API 存在、返回 `true`、但没有接马达，所以 `typeof navigator.vibrate === 'function'` 在鸿蒙上是**假阳性**，网页端无法自查。<br>**因此：想要马达震动 = 必须原生**（HarmonyOS 4.x 还能装 APK → Android 壳 + 原生振动桥；NEXT 只能走 ArkTS 的 `@ohos.vibrator`）。**纯网页能做的只有"确认输入"本身**：声音（Web Audio）或视觉。<br>**无论如何都不能只靠震动**：形变 `scale(0.94)` + 变暗 `brightness(0.82)` + 翻页高亮不依赖马达，任何设备上都在。<br>**用户决定（2026-09-26）**：鸿蒙上既然拿不到马达，就**先不加**替代品（点击音 / 更强的视觉痕迹）——现有三条反馈先用着；"点击音（默认关的开关）"与"Android 壳 + 原生振动桥"留作以后真觉得影响使用时再做，不提前造 |
| **D26** | **默认色 = 白色 `#ffffff`**（D24 的中性灰再往前一步，和浅灰页面是同一套）；字色由 Bridge 逐格下发（`ink`，浅底深字/深底白字） | 用户："按钮的默认颜色改成和页面适配的浅色"。白键在冷灰底上就是 iOS 分组列表那种观感；字色必须跟着走，否则白底白字。~~按下/松手的内圈用 `currentColor`~~ → 内圈已被 D27 删除 |
| **D27** | **按下与松手都**不画描边/内圈（`box-shadow` 一律去掉）：按下的证据只有**尺寸**（`scale(0.94)`）和**明暗**（`brightness(0.82)`），松手后的痕迹只用"压暗一点点"（`brightness(0.93)`）保留 220ms | 用户："点击时在按钮边上出现的高对比度边框非常丑，删了"。教训：内圈（`inset box-shadow`）会把圆角按钮切成一个方框，白底上跟随字色的那圈近黑尤其刺眼。**"按得出来"和"画个框"是两件事**——前者靠形变与明暗就够，边框是我想当然加的装饰 |
| **D28** | 灰阶令牌**带一点点蓝**：`--bg #eaecf2`（蓝-红 = +8）、`--fill #e2e5ee`（+12）、`--label #1c1e26`；纯白卡片不变 | 用户："整体配色饱和度为零有点丑，给整体色调加一点点蓝，只要一点点一点点一点点"。纯中性灰就是那个"饱和度为零"，看着发脏；iOS 自己的分组底 `#F2F2F7` 也是冷灰。**量级受测试约束**：蓝-红必须 > 0 且 ≤ 16，再大就变紫了 |
| ~~**D29**~~ | **PC 端按下确认灯（已撤回）**：Bridge 记下"按了哪一个"，已有的置顶精简窗整窗闪绿 200 ms 并显示 `▶ 停止   N36`；展开态只在状态行显示文字 | 做出来了，**用户真机看完一句"这个 pc 的提示界面有点过于丑陋了……无法接受，取消 pc 上的提示吧"就撤了**。教训：**"能用"和"能看"是两件事**——我按"余光可见"选了整窗换底色（`#00E676`），在 420×84 的置顶小窗上就是一块刺眼的荧光绿，而那个窗口本来就在 DAW 角落一直亮着。撤回范围：Bridge 的 `pad_flash` 记录、Tk 的闪灯与文字、`PAD_FLASH_*` 常量、相关测试与断言全部删掉。**保留**同一轮里修掉的那个显示 bug（面板音符原来显示成 `CCN39 127` + 进度条谎报满格，现在显示 `Note N39` + 进度条留空）|
| **D30** | **PC 端记忆**：①**两个窗口**的尺寸与位置都记（`standard`/`standard_pos` + `compact`/`compact_pos`）；②记住**上次选的 MIDI 输出端口与面板端口**，下次打开自动选回；③删掉面板端口后面那一段说明文字 | 用户："在 pc 端打开时我希望能够记录上一次的 midi out 和面板端口，把面板端口后面那一段文字去掉"＋"记住用户上一次调整的软件 ui 大小及位置"。⚠️ 第 ① 条**推翻了早期契约**"标准窗固定 480×420 且不记忆位置"（那是八轮真机反馈换来的）——用户现在明确要求记，所以改了，并在测试里把旧断言换成了新断言。实现上踩了两个坑：**记"当前窗口"必须用我们请求过的尺寸/位置**（`_win_size/_win_pos`），不能用 `geometry()`（未映射时它给的是被 minsize 钳过的值，会形成"越记越小"的回授）；**切模式时要记在"当前显示的那个模式"的键上**（`_built_compact`），不能记在已经翻过去的 `_compact` 上 |
| **D31** | **音符不再自由输入**：删掉编辑器里的音符输入框，音符恒为 **`36 + 触发编号`**（位置派生）；旧配置里手改过的音符也一律按位置重算 | 用户："删除音符自由输入的功能，仅使用软件提供的默认值"。副作用是**好的**：拖动换位只搬文字与颜色，音符留在位置上，于是**换位置不需要在 DAW 里重学**；音符也不可能再重复（48 格 = 48 个不同音符），"重复音符"提示自然退化成死代码 |
| **D32** | **PC 端字体**：中文控件用**等线**（`DengXian`），纯英文/数字控件（端口名、CC 值、START/QUIT、作者行、格子里的 `N36`）用 **Times New Roman**；字号沿用原值 | 用户："修改 pc 端的字体为等线字体，英文字体用 Times New Roman"。Tk 的字体只能指定**一个家族名**、没有 per-glyph 回退，所以按"这个控件上的字是什么"来选（混排的一律用等线，它自带拉丁字形）。等线在 Tk 里以本地化名"等线"注册，`DengXian` 这个 ASCII 名也能解析到（已实测） |
| **D33** | **手机端改成"首页 = 功能模块列表"**（应用名 **MIDI Deck**）：`/` 只列模块，**Digital Fader 挪到 `/fader.html`**，Shortcut Pad 仍在 `/pad.html`；将来加功能就加一行 | 用户："重做页面路由：进入主页应当显示不同的功能模块，当前应用模块有手机推子和模拟按钮，未来还会加入其他功能"。连带改动：Bridge 界面显示的网址仍是根地址（首页）；各页导航统一回 `← MIDI Deck`；校准页返回链接指向 `/fader.html?mode=X` |

## 4. 行为规格

### 4.1 面板

- **每页固定 2 列 × 4 行 = 8 格**（2026-09-26 由 4×2 改：扁而宽的按钮浪费手机竖向空间，见 D15）；**页数固定 6 页 = 48 个按钮**（D18，不可增删）。
- 每页有一个**大标题**（说明这页的宏是干什么的），其次是 8 个格子。
- **页切换用底部页签**（6 个页签常驻）。不用左右滑动：滑动与点击在同一块屏上容易互相误判。
- 手机与平板**共用同一套逻辑布局**，平板按屏幕等比放大（不做"按宽度自适应列数"——那会让 PC 端镜像失真）。
- 格子**铺满整屏**：2 列 4 行铺满后每格接近方形且明显更大。

### 4.2 单个格子

- 显示：**只有文字标签**。**音符编号不在手机上显示**（D19），只在 PC 编辑器里显示。
- 可配置：**文字**、**颜色**（任意合法 hex，D20）、**音符编号**，逐格独立；颜色无语义，纯为了快速认出。
- **按下即发**一次触发（瞬时）；不做长按/双击/连发手势，也不做误触保护（使用姿势是**看着手机操作**）。
- 按下时给出**视觉反馈**（高亮），作用是"确认已经发出"。
- **复合逻辑写在 DAW 的宏里，不写在按钮上**（见 D10）。

### 4.3 连接与失败

- 未连接 Bridge：整页显示"未连接"，格子不可点（避免用户以为已经发出去了）。
- 编辑同步（**布局下发 Layout Push**）：PC 端保存后立即广播；手机若此刻未连接，下次连上时收到当前布局。
  每一端都收到同一份布局。**v1 必做**。
- **不是**状态回读（**State Read-back**）：DAW 把"某个宏现在是开还是关 / 当前轨道名"发回手机并显示在按钮上——
  这是**反方向**的另一条链路（需要 Bridge 具备 MIDI 输入），**v1 不做**，见 §6。

## 5. 协议与数据（草稿）

**手机 → Bridge**

```json
{ "kind": "trigger", "id": 3 }
```

- 按下 = 一个触发；Bridge 侧的动作表决定发什么（Note On，通道 16；抬起发 Note Off）。
- **音符取哪一条**：优先用该格自己的 `cells[i].note`（D16），没有就按位置取 `36 + 触发编号`。**按住期间改过编号也不影响松开**——松开用的是按下时实际发出的那一条。

**Bridge → 手机**（沿用现有 `{"type": ...}` 形状）

```json
{ "type": "pad_layout", "layout": { "pages": [ { "title": "轨道颜色", "cells": [
  { "text": "变红", "color": "#b91c1c", "ink": "#ffffff", "note": 36 }
] } ] } }
```

- 连接时推一次，每次编辑后再广播。
- 一格的字段：`text`（≤24 字）、`color`（任意合法 hex，非法值退回默认）、`ink`（字色，**派生**字段）、`note`（0–127）。
- `ink` **只在发往手机的那份里出现**（`pad_layout_payload()` 在下发时算），`pad.json` 里不存：它完全由 `color` 决定，
  存起来就会和 `color` 不同步（改色忘了改字色 = 白字白底）。手机是哑显示端，不做颜色推理（D7/D12）——收什么用什么。
  旧的手机会忽略这个字段（前向兼容），新的手机缺这个字段时退回深色字。

**持久化**：`%APPDATA%\phone-midi-bridge\pad.json`（首次运行若不存在，用内置默认布局）。
读取时一律清洗：缺 `note` 按位置补，越界/非整数/重复的 `note` 退回默认值，坏 JSON 整体退化为默认布局。

## 6. 不做（非目标，v1）

- **不回读 DAW 状态**（**State Read-back**：不做按键 LED、"这个宏现在是开还是关"、当前轨道名回显）：
  方向是 DAW → Bridge → 手机，而 Bridge 目前**只有 MIDI 输出**，没有任何 MIDI 输入能力，回读是一条全新链路。
  另有一个具体障碍：loopMIDI 是**回环**端口——Bridge 一旦把同一个端口开成输入，就会收到**自己刚发出去**的
  CC/Note（自回声），回读得先解决端口划分问题。
  ⚠️ 注意与**布局下发（Layout Push）区分**：PC 改文字/颜色即时同步到手机是 **Bridge → 手机**，**属于 v1**。
- 不做 Stream Deck 式的图标、多动作、嵌套文件夹、DAW 原生命令库。
- 不做键盘注入（保留为 Bridge 动作表里的一种可选动作类型，见 §8 Q3）。
- 不改动主页 A/B/C 的任何链路、窗口契约与手感。

## 10. 推子页底部的第 4 页条（CC 廊）

> 2026-09-27。用户：「我希望在使用 Digital Fader 的 Mode A 和 Mode B 时，手机页面底下空白部分能够
> 显示第 4 页的八个按钮，方便快速在 DAW 中显示 CC 廊。至于快捷键映射的操作我会自行在 DAW 中设置。」

### 10.1 已定的决策

| # | 决策 | 依据 |
|---|------|------|
| **D37** | **第二处格子宿主**：`/fader.html` 的**运行界面**底部放 Shortcut Pad **第 4 页**那八格（编号固定 **24–31**），**只有 A/B 出现**（C 要摇晃手机，按不了屏幕）。第 4 页当"CC 廊开关"是**用户侧的约定**，不是配置项（不做"选哪一页"的设置） | 用户点名的场景就是"用 A/B 推子的时候想顺手切 CC 廊"。收在运行界面：推子页只在按了「启动」之后才连 Bridge，那里本来就有 WebSocket 与布局，零新增链路；设置界面不该摆演奏用的东西 |
| **D38** | 这一块**只占很小一块，绝不铺满**：形状与第 4 页同构（2 列 × 4 行，位置一一对应），但格子压到 **46px 高**、整块 **225px**，行高写死、不抢剩余空间；**不复用** `/pad.html` 那套铺满整屏的网格 | 用户：「不能复用已有的布局，因为已有布局占据全屏，而在 fader 的页面中我只需要占据很小的一块范围显示八个按钮」。推子页的主角仍然是推子：大数值、进度条、映射行、发送按钮的位置与大小都不许被挤。**尺寸是量出来的**（无头渲染 + `getBoundingClientRect`）：390×844 下这一块 225px，**加不加都不动发送按钮的下沿**；当时推子自身内容约 600px，52px 格子那版合计 874（比 844 多 30px，页面得滚一下）→ 取 46px（仍高于 44px 的可点下限）。<br>2026-09-27 推子页精简（删"映射 CCx Chx"行、大数字减半）后内容降到 **约 683px**，底部反而多出约 160px 空白；**这一块的大小没有跟着放大**——用户要的是"顺手按得到"，不是"占满"（真觉得小再调，就一个数） |
| **D39** | 内容与编号**全部走既有的 `pad_layout`**（连接时下发 / 编辑后广播），按下仍是 `{kind:'trigger', id}`。**不新增协议、不新增 HTTP 接口、Bridge 侧零改动**——推子页本来就是 `/ws` 的一个客户端，以前只是把这条消息忽略了 | 复用是这里唯一正确的做法：一格的文字/颜色/编号只有 Bridge 一个写入方（D7），再做一条读取路径就是第二个真相来源。合成一条 Note 的规则不变（ADR 0004），所以**在哪儿按都发同一条 Note**——面板第 4 页与推子页那八格在 DAW 侧共用同一套映射 |
| **D40** | 两处格子**共用一份实现**：新增 `web/padgrid.js`（建格 / 绘制 / 按下与松开 / 离线拒按 / 震动确认 / 松手痕迹），`pad.js` 改为调用它。页面只管自己的事——面板管 6 页与页签，推子页管"哪一页 + 什么时候露面" | 这是本次**重构**的落点。这套逻辑原本长在 `pad.js` 里，第二处要用就只能抄一份；抄一份的下场是"改了一处忘了另一处"（本项目已经吃过：Mode C 的校准链接、`ink` 与 `color` 不同步）。共用后 `COLS/ROWS`、编号公式、离线规矩、震动档位都只有一个定义 |
| **D41** | 边角状态：**布局没到 → 整块收起**（不摆八个没有内容的空格子）；**未连接 → 变灰不可按**、按下不发消息也不给震动（与面板同一套规矩，见 §9 的 Q-e）；**断连**时先把按住的格子松开再断开引用（Bridge 侧另有 1s 兜底）；**空文字的格子与面板完全一致**（没填就空白，用户选的这一档）；条上方显示第 4 页的**标题**小字（跟着布局走，一眼知道镜像的是哪一页） | 空文字的取向要和面板一致，否则同配置两端看起来不一样；标题是"这八格是什么"的唯一线索，而它不是说明文字（用户删的是介绍段落，不是标识） |

### 10.4 明确不做

- **不做"选哪一页"的设置**：第 4 页 = CC 廊是用户侧的固定约定（D37）；真需要时再加，那时也只需要加一个字段。
- **不做长按/双击/连发**：与面板同一取态（D12）。
- **不做状态回读**（按键高亮"这条 CC 廊现在是显示还是隐藏"）：仍然需要 Bridge 具备 MIDI 输入，见 §6。
- **不改 Bridge**：这一版前端零协议改动（D39）。
